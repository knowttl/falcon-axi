written against was ported and removed at stage 1.

## 0. Invariant R: v1 is read-only, with four captain-granted exceptions

**falcon-axi v1 changes no state in a Falcon tenant.
It requires only CrowdStrike read permissions, and it implements no write, create, update, delete, execute,
containment, quarantine, release, response, or otherwise mutating operation, with the four exceptions the
captain granted: starting and stopping an NG-SIEM search job (N1, §4.3), and sending fixed read-only query
documents to the Identity Protection GraphQL endpoint, whose scope Falcon labels write (N2, §4.4),
a guarded single-host RTR read-only command lifecycle (N3, §4.5), and bounded MalQuery exact/fuzzy pattern searches (N4, §4.6).**

This is a first-class architectural invariant, not a default posture and not a v1 convenience.
It is captain-confirmed and binding, it is not this document's to relax, and any argument for relaxing it is a
captain decision.
N1, N2, N3, and N4 are such decisions, made by the captain and recorded here.
None is a precedent an agent may extend; N2 is not general write authority, and N3 admits only its named operations and command allowlist.
Every clause outside those closed exceptions stands exactly as before.

Invariant R is load-bearing in six places, and each states it in its own terms rather than deferring to this
one:

| Where | What it says |
| --- | --- |
| §1.5 | The excluded capability classes, named as command-surface non-goals |
| §2.2 | Every included endpoint carries two citations proving what its scope is |
| §3 | Read-only is semantic, not method-based, and the transport is the enforcement point |
| §4 | The excluded mutation surface and the four closed exceptions, including N3's guarded live-host execution |
| §5.7 | Read scopes plus only N1/N2/N4's write-labelled scopes; the RTR and RTR audit read scopes only for their named operations, with execution separately opted in |
| §15 | No live test authorization is implied; future live validation must stay inside N1, N2's documents, N3's confirmed lifecycle and cleanup boundary, and N4's bounded pattern searches |

**Read-only is semantic, not syntactic.**
The HTTP method is not proof of safety in either direction.
The registry in §2.1 includes POST requests that are pure reads, because Falcon posts an ID list in a
request body when it is too long for a query string, or because that is the documented hydrate verb.
Meanwhile Falcon has read-*scoped* operations with real side effects (§4.1).
So neither the verb nor the scope name alone decides inclusion; §2.2 states the two-citation rule that does,
and §3.3's exception tiers confine the write-labelled scopes to N1, N2, and N4.
N3 requires a fourth tier because its read scope permits real execution on a live host.

## 1. Scope and command surface for v1

### 1.1 The shape of the upstream surface

`CrowdStrike/falcon-mcp` at commit `7c2749a` registers **154 tools and FQL-guide resources across 24 domain
modules** (`falcon_mcp/modules/`, counted by `grep -c 'name="'`).
That is the breadth benchmark, and v1 deliberately does not chase it.

The modules are: cases, cloud, correlation_rules, custom_ioa, data_protection, detections, discover,
exclusions, firewall, host_groups, hosts, idp, intel, ioc, ngsiem, policies, quarantine, recon, rtr,
scheduled_reports, sensor_usage, serverless, shield, spotlight.

A large share of that surface is mutating: falcon-mcp registers `create_*`, `update_*`, `delete_*`,
`perform_*`, and RTR execution tools across cases, cloud, correlation rules, custom IOA, exclusions, firewall,
host groups, IOC, policies, quarantine, shield, and detections.
None of it is admitted beyond the closed captain exceptions in §4.

### 1.2 Shipped read domains, plus NG-SIEM search and the identity directory under captain exceptions N1 and N2

v1 buys depth in the reads that an analyst or an agent chains during triage, including read-only cloud inventory and posture.
Sensor usage and Falcon Recon extend these reads as specified in §2.4.
`cve` is the fourth read: a query-and-hydrate list and a single-CVE detail view.
`account` is the fifth: the Discover accounts inventory, admitted by the captain together with
`host logins`, with the corroboration §2.2 accepts when falcon-mcp has no tool.
NG-SIEM search joined them at stage 3 by captain decision, not by the reasoning below: its entry price is a
write scope, and §4.3 records why the captain paid it.
The Identity Protection directory joined at stage 4 by the same kind of decision (N2, §4.4): the endpoint that
serves it is scoped `WRITE` for reads, and the captain accepted that scope against fixed read-only queries.
Custom IOC and host-group reads are specified in §1.4.1.

`detection process <id> [--full]` projects the triggering process and the alert's top-level `parent_details` and `grandparent_details` into lineage rows with `relation`, `filename`, `filepath`, `cmdline`, `sha256`, and `process_id`.
It exposes `triggering_process_graph_id` separately as a pivot, without fetching a graph or claiming complete ancestry.
Missing ancestors state `no parent recorded` or `no grandparent recorded`; `no process recorded for this detection` appears only when triggering process fields, the graph pivot, and both ancestor records are absent.
Recorded ancestors remain visible when triggering process fields are absent.
Missing scalar fields remain `unknown`; command lines are redacted before the 800-character preview and `--full` expands them, with a hint only when truncated.
The view uses the existing `PostEntitiesAlertsV2` hydrate and `Alerts:read`, with no new operation or scope and no change to `detection show`.
Section 13 owns the request cost.
Field evidence is CrowdStrike's [generated alert model](https://github.com/CrowdStrike/gofalcon/blob/main/falcon/models/detects_alert.go), including `DetectsAlertParentDetails` and `DetectsAlertGrandparentDetails`, checked 2026-10-22.
Synthetic offline fixtures and recorded invocations establish deterministic rendering, without tenant validation.
Recorded valid SHA-256 hashes suggest `sandbox list --sha256 <hash>` to read existing sandbox reports.

`sandbox list --sha256 <64-hex-hash> | --filter <FQL>` reads existing report identifiers through `QueryReports`, then hydrates `GetSummaryReports` and restores query order.
Exactly one selector is required; hash validation happens before authentication and builds `sandbox.sha256:'<hash>'`.
The hash FQL field is partner-corroborated by the [XSOAR CrowdStrikeFalconX integration](https://github.com/demisto/content/blob/master/Packs/CrowdStrikeFalconX/Integrations/CrowdStrikeFalconX/CrowdStrikeFalconX.py), not documented as a filter field by CrowdStrike.
Lists project `id`, report `verdict`, environment `threat_score`, `environment_description`, `submit_name`, and report `created_timestamp`, with one row per sandbox environment.
Reports without environment records retain one row with unknown environment fields.
Counts and offset cursors refer to reports, not environment rows; `--limit` defaults to 20 with a documented 5000 ceiling, and credential-bound cursors preserve the selected hash or FQL.
`sandbox show <report-id>` reads the same summary endpoint, preserving every environment and adding `file_type`, `classification_tags`, `submit_url`, and `sha256`.
Both views omit CID, user identity, and artifact handles; submit URLs appear only in detail.
Empty queries explicitly say `not licensed or no data`, explaining that only existing tenant submissions have reports.
Empty detail results and 404s are `NOT_FOUND`; mismatched or omitted hydrated identifiers are `UPSTREAM_ERROR`.
A 403 names `Sandbox (Falcon Intelligence):read` and Falcon Intelligence (Sandbox), with the console-picker visibility caveat inferred as in §17.17.
These are ordinary read operations under Invariant R, with no submission, upload, artifact or sample download, report deletion, or new exception.
Validation is offline using wholly synthetic documented response shapes, with no live-tenant claim.
The intentional recorded-output additions are sandbox discovery and scopes, and detection lineage hash suggestions.

`process show <pid-id> [--full]` reads one observed process using `entities_processes` under `IOCs (Indicators of Compromise):read`.
The identifier must match PSFalcon's `pid:<32 hex device ID>:<decimal ID>` shape and is validated before authentication.
The documented response is a direct array, with nine fields: `command_line`, `device_id`, `file_name`, `process_id`, `process_id_local`, `start_timestamp`, `start_timestamp_raw`, `stop_timestamp`, and `stop_timestamp_raw`.
The detail renders those fields, with absent values as `unknown`, and redacts command lines before their 800-character preview.
Truncated previews include a `--full` hint; `--full` prints the complete redacted command line without that hint.
An empty array or 404 is `NOT_FOUND` with an `ioc processes <type:value> --host <device_id>` remedy; malformed or mismatched detail responses are `UPSTREAM_ERROR`.
A 403 is `SCOPE_DENIED` naming the read scope and explaining that subscription or client permissions can prevent access, without asserting a particular license requirement.
IOC process lists suggest `process show <process_id>`; detection lineage suggests details only for recorded graph or process identifiers matching that shape, without synthesizing identifiers from numeric PIDs.
No graph traversal or additional request occurs in either pivot view.
These behaviors use synthetic fixtures only and make no tenant-validation claim.
The intentional recorded-output changes are the IOC process-list suggestion plus command discovery and scopes, recorded in their golden scenarios and command reference.

`file-change list [--filter <FQL>] [--limit N] [--cursor <token>]` reads FileVantage change history using `highVolumeQueryChanges` and `getChanges` under `Falcon FileVantage:read`.
The query is `GET /filevantage/queries/changes/v3`, sorted `action_timestamp|desc`, with the common default of 20 rows and a ceiling of 5000.
Its opaque `after` continuation uses the existing token cursor model, bound to operation, filter, sort, region, selected tenant and credential; an empty ID page terminates continuation.
Hydration is `GET /filevantage/entities/changes/v2` in batches of at most 500 IDs, restoring query order and retaining the query's pagination metadata.
Missing totals remain unknown.
Default columns are `action_timestamp`, `action_type`, `entity_type`, `entity_path`, `host`, and `severity`; `host` projects `host.name`, and a parallel `change_ids` array makes each row addressable without expanding those columns.
`file-change show <id>` adds the identifier, `process_id`, `process_image_file_name`, `command_line`, `parent_process_image_file_name`, `grandparent_process_image_file_name`, and `diff`.
The official example specifies `host` and `diff` only as objects; `host.name` follows its documented FQL example, while diff is preserved as supplied and no nested diff schema is asserted.
CID fields are omitted or redacted by the common output boundary.
An empty list explains that no matching data or missing Falcon FileVantage licensing can cause the result.
A 403 maps to `SCOPE_DENIED` naming the read scope and licensing note; a missing detail maps to `NOT_FOUND` suggesting `file-change list`.
Omitted query IDs during hydration and nonempty detail responses lacking the requested ID fail as `UPSTREAM_ERROR`; genuinely empty detail responses remain `NOT_FOUND`.
A rejected FQL filter maps to `FQL_INVALID` with the example `host.name:'SYNTHETIC-HOST'`.
Only these two pure reads are admitted; `getContents`, its separate `Falcon FileVantage Content:read` scope, configuration reads and all writes remain absent.
Documented resource arrays and SDK resource envelopes are accepted; malformed resources and error-bearing 200 responses fail as `UPSTREAM_ERROR`.
Validation is exclusively synthetic and offline, with no tenant or license validation claim.
The intentional output additions are command discovery and scopes; existing golden output templates expand their command-reference rows, and new FileVantage scenarios pin the domain output.

`malquery show <sha256>` reads indexed file metadata through `GetMalQueryMetadataV1` with a single SHA-256 in `ids`.
The hash must contain exactly 64 hex characters, is validated before authentication, and is normalized to lowercase for lookup.
The detail projects the eight documented fields: `family`, `filesize`, `filetype`, `first_seen`, `label`, `md5`, `sha1`, and `sha256`.
Absent fields remain `unknown`; direct-array success responses and resource envelopes are accepted, while malformed, error-bearing, or mismatched metadata fails as `UPSTREAM_ERROR`.
An empty metadata array succeeds with `0 indexed files for that SHA-256`, explaining that no data or missing Falcon MalQuery licensing can cause an empty result.
`malquery quota` reads `GetMalQueryQuotasV1` and projects `meta.days_left`, download/hunt/monitor counts and limits, `download_counts`, `hunt_counts`, and `refresh_time`, preserving zero values and leaving absent fields unknown.
Missing quota metadata fails as `UPSTREAM_ERROR`; it never invents zero counters.
Both are pure GET reads under `MalQuery:read` and Invariant R, with no new exception and no quota-consuming search, hunt, or download.
A 403 names the read scope and Falcon MalQuery licensing, retaining §17.17's inferred console-picker visibility caveat.
Section 4.6 owns the later search/status surface and its exclusions.
Validation uses only documented synthetic fixtures, without contacting a Falcon endpoint or claiming live license validation.
The intentional recorded-output changes add MalQuery command discovery and its read scope to the shared command-reference and scopes documents.

#### 1.2.1 Cloud inventory and posture

`cloud-asset list|show` reads CSPM cloud assets, distinct from Discover endpoint assets.
`iom list|show` reads individual Indicators of Misconfiguration.
`cloud-risk list` reads aggregated cloud risks.
All five operations are ordinary `effect: read` rows, requiring respectively `Cloud Security API Assets:read`,
`Cloud Security API Detections:read`, and `Cloud Security API Risks:read`.
There is no registration, remediation, suppression change, or other tenant mutation.

Lists accept `--filter`, `--sort`, `--limit` (§7.3), and the common opaque `--cursor` (§7.2).
Assets query IDs using an `after` token from top-level `meta.next`; IOMs query IDs by offset.
Both hydrate in GET batches of at most 100 IDs and restore query ordering, retaining query pagination metadata.
Risks use a single combined read paginated by offset.
Missing totals stay unknown, and empty results do not imply an invented total.
No new `--all` walk is introduced on these domains.

Default asset rows contain `id`, `resource_name`, `resource_type`, and `cloud_provider`.
IOM rows contain `id`, `evaluation_severity`, `evaluation_status`, and `resource_id`.
IOM values come from `evaluation.severity`, `evaluation.status`, and `resource.id`, preserving the finding ID separately.
Risk rows contain `id`, `rule_name`, `severity`, and `status`.
Asset and IOM detail views add selected scalar resource and security context without raw configuration or benchmark blobs.
They do not print tenant CIDs.

Risk detail is deliberately absent.
The [official combined risk read](https://developer.crowdstrike.com/api-reference/collections/cloud-security/#combined-cloud-risks)
and falconpy `_endpoint/_cloud_security.py` document neither a risk-detail operation nor an ID filter.
The separate [Cloud Security Risks collection](https://developer.crowdstrike.com/api-reference/collections/cloud-security-risks/)
and falconpy `_endpoint/_cloud_security_risks.py` expose only an enriched asset timeline by ID, which is not a substitute.
Consequently neither help nor scope discovery advertises `cloud-risk show`.

Parity evidence is CrowdStrike's `falcon_mcp/common/api_scopes.py` and
[`modules/cloud/cloud_assets.py`](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/cloud/cloud_assets.py),
[`cloud_base.py`](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/cloud/cloud_base.py),
[`cloud_iom.py`](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/cloud/cloud_iom.py), and
[`cloud_risks.py`](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/cloud/cloud_risks.py),
cross-checked with falconpy's generated endpoint tables and the official
[Assets](https://developer.crowdstrike.com/api-reference/collections/cloud-security-assets/) and
[Detections](https://developer.crowdstrike.com/api-reference/collections/cloud-security-detections/) references on 2026-10-18.
Offline fixtures are wholly synthetic; these commands are matched to those sources and are not tenant-validated.

### 1.2.2 Exclusion and quarantine inventory reads

`exclusion list --type ml|ioa|sensor-visibility|certificate` queries ids and hydrates records in query order.
`exclusion show <id> --type ...` reads one record from the same inventory.
The discriminator is required for both commands; ids alone do not identify an exclusion API.
`quarantine list` and `quarantine show <id>` read file metadata, never release or delete files.
`ActionUpdateCount` is absent because action previews have no use without actions.

Lists take raw `--filter`, `--limit` (default 20), and a signed `--cursor` bound to the operation, filter,
origin, client, and tenant using §7.2's existing offset model.
Exclusion queries cap at 500 except certificate queries at 100; quarantine caps at 500 following falcon-mcp.
Quarantine sends its offset as a string and entity ids as a POST body; exclusions send both as query parameters.
The query total survives hydration, and missing entities do not change the next query offset.
An absent total prints `unknown` and offers continuation only for a full query page.
Empty lists state zero results and skip hydration; absent detail records return `NOT_FOUND`.

Default exclusion rows contain `id,value,applied_globally` for ML and sensor visibility,
`id,name,pattern_id` for IOA, and `id,name,status` for certificates.
Quarantine rows contain `id,hostname,sha256,state`.
Detail views return the selected metadata record through §5.5's redaction boundary.
Filter help follows falcon-mcp's `resources/exclusions.py` and `resources/quarantine.py`.
In particular, unsupported exclusion fields may silently return no matches, and exclusion value/name
substring filters use the `:*` operator.

The closed registry adds only ten `effect="read"` operations: ML `exclusions_search_v2`/`exclusions_get_v2`,
IOA `ss_ioa_exclusions_search_v2`/`ss_ioa_exclusions_get_v2`, sensor visibility
`querySensorVisibilityExclusionsV1`/`getSensorVisibilityExclusionsV1`, certificate
`cb_exclusions_query_v1`/`cb_exclusions_get_v1`, and `QueryQuarantineFiles`/`GetQuarantineFiles`.
Each carries an official collection scope citation plus falcon-mcp `common/api_scopes.py` and the consuming
`modules/exclusions.py` or `modules/quarantine.py` citation.
The scope mapping is Machine Learning Exclusions:read for ML and certificates, IOA Exclusions:read,
Sensor Visibility Exclusions:read, and Quarantined Files:read.
The two exception allowlists and transport enforcement are unchanged.
Evidence was checked against the official API reference, falcon-mcp, and falconpy 1.6.5 on 2026-10-18.
Offline fixtures and goldens are synthetic; these commands have no tenant validation claim.

### 1.3 Deferred, with the reason

Deferring is a decision, not an omission, so each carries its reason.
None of these is deferred *because* of Invariant R alone; the classes excluded by Invariant R are in §1.5.

- **remaining intel reads.**
  Actor and report list/show, `cve list|show`, `indicator list|show`, and malware families ship.
  Indicator retrieval implements the `_marker` pagination model (§7.1).
  Spotlight vulnerability metadata and supported-evaluation remain deferred.
- **Shield beyond posture checks.**
  `shield list` and `shield show` ship; alerts, inventories, activity, and administrative reads remain absent.
  Dismissals and all other writes stay excluded by Invariant R.
- **idp, beyond the reads in §4.4.**
  `identity list`, `identity show`, and `identity timeline` shipped at stage 4 under captain exception N2 (§4.4),
  over the GraphQL endpoint (falcon-mcp `api_preempt_proxy_post_graphql`) that earlier drafts of this section
  deferred as not fitting the entity/query request shape.
  It fits the transport mechanically, as one fixed POST route with a body falcon-axi builds from a closed
  document registry; what made it a decision rather than an implementation detail was its write-labelled scope.
  Assessment and REST sensor inventory are also implemented; §4.4 owns their contracts.
  Policy-rule REST reads also ship (§2.3).
  Still absent: standalone GraphQL incidents and every GraphQL mutation.
- **ngsiem.**
  Admitted at stage 3 by captain exception N1, reversing the §4.3 exclusion below.
  falcon-mcp maps `StartSearchV1` and `StopSearchV1` to **`NGSIEM:write`** and `GetSearchStatusV1` to
  `NGSIEM:read`, so the three search lifecycle operations are all v1 ships of that collection: no ingest,
  no lookup-file write, no parser mutation, no dashboard, and no saved query.
- **rtr beyond N3, scheduled_reports.**
  Excluded by Invariant R, see §4.1 and §4.2.
  See §4.5 for N3's delivery boundary and §19 for its implementation slices.

### 1.4 Naming and grouping

Nouns are singular and each takes subcommands: `falcon-axi detection list`, `falcon-axi detection show <id>`.
This matches `azure-axi` (`resource list` / `resource show`) and `awx-axi` (`job list` / `job show`), so an
agent that has used one AXI tool in the fleet already knows the shape.

Falcon's own vocabulary is inconsistent here: the product surface is "detections", the current API collection
is "Alerts", and falcon-mcp's module is `detections` while its scope is `Alerts:read`.
falcon-axi standardises on `detection` as the noun and says `Alerts:read` in scope output, because the scope
string is what an operator pastes into the Falcon console and it must match the console exactly.

Every verb in the CLI is a read verb, apart from N1's searches (§4.3), `rtr run` under N3 (§4.5), and `malquery search` under N4 (§4.6).
The GraphQL commands in §4.4 send read queries through a write-labelled scope under N2.
There is no `contain`, `update`, `assign`, `close`, `release`, `execute`, `create`, or `delete` verb
anywhere in the surface; N1's commands only create, read, and cancel a query job in the caller's own
tenant and nothing else (§4.3), and §3.3 makes both facts structural rather than stylistic.

Run `falcon-axi --help` for the command tree generated from the command declarations.
Run `falcon-axi <group> --help` to list that group's subcommands and one-line summaries, including nested groups.
Group help is authentication-free and exits successfully, including for `setup`, which is also a standalone command.
The [README's generated command reference](../../README.md#commands) owns delivery status; §12 owns `setup` and `setup hooks`.

### 1.4.1 Custom IOCs and host groups

`ioc list [--filter <FQL>] [--limit N] [--cursor <token>]` queries custom indicator IDs with `indicator_search_v1`, then hydrates them with `indicator_get_v1`, restoring query order.
This follows [falcon-mcp's search_iocs](https://github.com/CrowdStrike/falcon-mcp/blob/ece8575/falcon_mcp/modules/ioc.py), rather than the equivalent combined endpoint.
The default four columns are `id,type,value,action`; `ioc show <id>` returns the indicator's configuration and metadata without creator identities or tenant CIDs.
The list defaults to 20 rows, its ceiling is 500, and continuation uses `meta.pagination.after` inside the existing credential-bound token cursor.

`ioc hosts <type:value>` returns observed device IDs through `DevicesRanOn`.
`ioc processes <type:value> --host <device_id>` returns process IDs through `ProcessesRanOn`, whose API requires a device ID.
The first colon separates the type from its value, preserving IPv6 values.
Types are `domain`, `ipv4`, `ipv6`, `md5`, and `sha256`.
Both reads use offset cursors, default 20 and ceiling 100.
falcon-mcp has no equivalent tools; the registry cites the official IOCs reference, falconpy's generated `_iocs.py` table and PSFalcon's `public/indicators.ps1` wrappers.
These commands return identifiers only and do not request process details or initiate report jobs.

`host-group list [--filter <FQL>] [--limit N] [--cursor <token>]` uses `queryCombinedHostGroups` with `name.asc` sorting and columns `id,name,group_type,description`.
`host-group members <id>` accepts the same flags, filters on host attributes, and uses `queryCombinedGroupMembers` with columns `device_id,hostname,platform_name,status`.
Both default to 20 rows, have a ceiling of 5000 and use offset cursors bound to the group ID and filter.
These request and response shapes match [falcon-mcp's host-group readers](https://github.com/CrowdStrike/falcon-mcp/blob/ece8575/falcon_mcp/modules/host_groups.py).
All six commands have synthetic offline fixtures and recorded-invocation coverage.
§15 owns the live-test boundary.
The scope matrix and help discovery gain these commands; no write, membership action or `GetIndicatorsReport` operation is registered.
Run `falcon-axi scopes` for their registry-derived permission requirements (§8.3).

### 1.6 The post-v1 extension path, marked unimplemented

For the avoidance of a future misreading: a mutation surface, if one is ever authorised, would be a
**post-v1 change gated on an explicit captain decision**, and it would require widening the `effect` union in
§3.3, adding a second enforcement tier, and reviewing §15's live-test boundary.
Captain exception N1 is exactly that process run once, for one capability, and it did all three of those
things: `effect` gained a second member, §3.3 gained the tier that confines it to two named ids, and §15.1
restated its boundary.
Captain exception N2 ran it a second time, for one GraphQL endpoint: `effect` gained a third member, §3.3 gained
a third tier that confines it to one named id, one scope, and a closed registry of documents, and §15.1
restated its boundary.
Captain exception N3 authorizes a fourth tier for exactly four RTR lifecycle ids, with a closed command allowlist and the guards in §4.5.

Captain exception N4 adds a fifth tier, `malquery-search`, for exactly two pattern-search ids, sealed to `MalQuery:write`, bounded validated bodies, and no hunt or download (§4.6).
Nothing else in v1 prepares for a wider surface, no placeholder exists, and these exceptions are not general licences:
admitting anything further is another captain decision, argued on its own terms.

### 1.7 Discover inventory and host network history

`asset list` reads `combined_hosts` and `asset show <id>` reads `get_hosts`.
The asset noun distinguishes Discover managed and unmanaged assets from the sensor-host inventory.
Use raw FQL `entity_type:'managed'` or `entity_type:'unmanaged'` to select either class.
`application list` reads `combined_applications`.
Both combined endpoints require an FQL filter according to the [official Discover reference](https://developer.crowdstrike.com/api-reference/collections/discover/) and [FalconPy endpoint definitions](https://github.com/CrowdStrike/falconpy/blob/main/src/falconpy/_endpoint/_discover.py).
When `--filter` is omitted, asset reads send `id:'*'` and application reads send `name:'*'`, using their documented wildcard fields for broad inventory reads.
Explicit FQL replaces the default, and cursors bind the effective filter sent to Falcon.
These two combined reads use `meta.pagination.after` with the existing token cursor model, a default limit of 20, and a ceiling of 1000.
The official Discover API reference and falconpy's generated table own these limits and pagination parameters; falcon-mcp's asset wrapper currently offers offset and 5000, so those two wrapper parameters are deliberately not followed.
`login list` reads `query_logins` with offset pagination, then `get_logins` with at most 100 query IDs, restoring query order and preserving the query total even if hydration returns fewer entities.
Its default limit is 20 and its ceiling is 100.
All three lists accept `--filter`, `--limit`, and `--cursor`; a cursor binds the filter, operation, credential, region, and tenant as in §7.2.
Asset rows contain id, hostname, entity_type, and platform_name; application rows contain id, name, version, and vendor; login rows contain id, username, hostname, and login_timestamp.
The asset detail view adds sensor association, OS version, criticality, current addresses, and observation timestamps.
Its `mac_addresses` list projects every available `network_interfaces[].mac_address`, as defined by the [Discover host model](https://github.com/CrowdStrike/gofalcon/blob/main/falcon/models/domain_discover_api_host.go), and is empty when no MAC data is present.
The asset and application list goldens deliberately change cursors to bind the effective default filter, their help documents describe that default, and the asset detail golden replaces the undocumented `current_mac_address` scalar with `mac_addresses`.
The Discover reads described in this section require only `Assets:read`.
`host network <device_id>` reads `QueryGetNetworkAddressHistoryV1` using body `ids: [device_id]` under `Hosts:read`, rendering the returned history without inventing address-entry fields or pagination parameters.
The API reference shows an array of device_id/history objects; gofalcon's `falcon/models/deviceapi_network_address_history_response_v1.go` documents the ordinary resources envelope, and both are accepted.
Its `deviceapi_network_address_v1.go` names the history fields ip_address, mac_address, and timestamp.
These reads are matched to the official API reference, falcon-mcp's `falcon_mcp/modules/discover.py`, and falconpy's `_endpoint/_discover.py` and `_endpoint/_hosts.py`, not tenant-validated.
For operations falcon-mcp does not expose, PSFalcon's `public/discover.ps1` `Get-FalconAsset` and `public/devices.ps1` `Get-FalconHost -Network` corroborate the registry rows.
The separate IoT inventory contract is in §2.3.
No mutation or transport-enforcement change is admitted here.
The golden gate deliberately changes command discovery, host subcommand discovery, and the scopes matrix, and adds D6 success and help documents.

## 2. Backend choice and the operations v1 speaks

falcon-axi speaks the CrowdStrike Falcon REST API directly over HTTPS.
(Amended by `docs/design/v1-python.md` §2: the runtime is Python 3.11 or newer and the HTTP client is
`crowdstrike-falconpy`, confined to one module. The reasoning below stands; only the language does not.)

There is no vendor CLI to wrap.
CrowdStrike ships SDKs (Python, Go, TypeScript, Rust, Ruby, PowerShell; the tab set on every operation page of
the Developer Center enumerates them) but no first-party general-purpose command-line client, so the "wrap the
official CLI" option that `awx-axi` weighed against awxkit does not exist here.
§16 evaluates the SDK path.

### 2.1 The complete v1 operation registry

[`falcon_axi/transport/operations.py`](../../falcon_axi/transport/operations.py) owns the complete registry,
including each operation's method, path, scope, effect, and required evidence.
Nothing outside that sealed registry can be issued (§3.3).
Command declarations in the domain modules select those operations; `falcon-axi scopes` projects their
command-to-scope mapping (§8.3).

The three NG-SIEM operations are the whole of captain exception N1 (§4.3), and the GraphQL operation is the whole of captain
exception N2 (§4.4).
Only N1's two `search-lifecycle`, N2's one `graphql-query`, and N4's two `malquery-search` operations may carry a write scope.
The NG-SIEM routes and the ThreatGraph process-summary route have path variables, which §3.3 property 7 validates before a request is prepared.
ThreatGraph's `vertex_type` is fixed to `processes` at that boundary.
The GraphQL operation takes no caller body at all: it takes the name of a registered query document and its variables,
and §3.3 property 8 builds the body.
N3's seven approved RTR operations are recorded with citations in §4.5; §19 records the shipped history and guarded execution slices.
They add no write-labelled scope and cannot reuse either N1's or N2's effect.

`POST /oauth2/token` is authentication rather than a scoped operation and is confined to the separately
sealed authentication path in §3.3.

### 2.2 The two-citation rule

The FileVantage entries cite the [official collection](https://developer.crowdstrike.com/api-reference/collections/filevantage/) for `Falcon FileVantage: READ` on `highVolumeQueryChanges` and `getChanges`.
falcon-mcp has no corresponding tool, so [falconpy's generated endpoint table](https://github.com/CrowdStrike/falconpy/blob/main/src/falconpy/_endpoint/_filevantage.py) and [PSFalcon `Get-FalconFileVantageChange`](https://github.com/CrowdStrike/psfalcon/blob/master/public/filevantage.ps1) corroborate the routes, read scope and limits.
The official 200 examples render resource arrays without scroll metadata; `meta.pagination.after` follows PSFalcon's generic scroll convention and remains unverified on a licensed tenant.
Both registry entries carry this evidence, checked 2026-10-22.

`process tree <pid-id> [--cursor <token>] [--full]` reads the process, up to five ancestors in nearest-parent order, and one level of children.
It adds only `combined_summary_get` (`GET /threatgraph/combined/{vertex_type}/summary/v1`) and `combined_edges_get` (`GET /threatgraph/combined/edges/v1`), both ordinary reads under `Threatgraph:read`.
The [official ThreatGraph reference](https://developer.crowdstrike.com/api-reference/collections/threatgraph/) states `Threatgraph: READ` for both operations and documents `parent_process`, `child_process`, the 100-edge limit and string `offset` continuation.
falcon-mcp has no tools for these operations; [falconpy's generated endpoint table](https://github.com/CrowdStrike/falconpy/blob/main/src/falconpy/_endpoint/_threatgraph.py) confirms their exact methods, routes and parameters, and [PSFalcon's ThreatGraph wrappers](https://github.com/CrowdStrike/psfalcon/blob/master/public/threatgraph.ps1) expose them through `Get-FalconThreatGraphVertex -IncludeEdge` and `Get-FalconThreatGraphEdge`.
Evidence was checked on 2026-10-22 without contacting Falcon endpoints.
The summary path parameter is named `vertex_type` internally to match falconpy and is restricted to the fixed value `processes`; callers cannot select another vertex type.
The successful resource schema is absent from the API spec.
The shape source is CrowdStrike's [falconpy SDK sample `samples/threat_graph/threat_finder.py`](https://github.com/CrowdStrike/falconpy/blob/main/samples/threat_graph/threat_finder.py): `resources[].id`, `properties`, and edge dictionaries containing lists of records with an `id` field.
Rows project `ImageFileName`, `CommandLine`, `SHA256HashData`, and `ProcessStartTime_formatted` as `filename`, `cmdline`, `sha256`, and `start_time`, retaining `id` and `relation`.
Missing property fields remain `unknown`; command lines are redacted before an 800-character preview, with `--full` and a hint only when shortened.
Missing parent edges stop cleanly; a repeated vertex stops with a cycle note, and a sixth ancestor is never requested.
The child read fixes `edge_type=child_process` and `limit=100`, without recursive child traversal or extra hydration requests.
CrowdStrike's [generated ThreatGraph paging model](https://github.com/CrowdStrike/gofalcon/blob/main/falcon/models/threatgraph_paging.go) supplies `meta.pagination.next_page`, passed back as `offset` inside the existing signed token cursor bound to process, operation, credential, origin, and tenant.
Continuation rereads lineage and fetches only the next child page, preserving `--full` in its suggestion when selected.
No child total is invented; empty child pages terminate continuation, and a repeated child offset is an upstream error.
A 403 names `Threatgraph:read` and explains that ThreatGraph API subscription access may be required, without claiming licensing was observed.
Help and fixture provenance disclose the SDK sample shape source; synthetic offline tests establish deterministic behavior, not tenant validation.

The configuration and case reads carry official collection scope citations in `transport/operations.py`.
Their corroboration is CrowdStrike's [firewall module](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/firewall.py),
[custom IOA module](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/custom_ioa.py),
[correlation rules module](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/correlation_rules.py),
and [cases module](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/cases.py),
with scope mappings in `falcon_mcp/common/api_scopes.py` and matching falconpy 1.6.5 endpoint tables.
These are source-matched, offline-tested reads, not tenant-validated features.

Per the binding addendum, **an endpoint may appear in v1 only if both of the following were established and
cited.**
An endpoint that fails either test remains unregistered until both citations are established.

1. **Official CrowdStrike documentation** for the endpoint and its required API scope, stating what that
   scope is.
   For every operation except the five the captain exceptions N1, N2, and N4 admit, that scope must be a read
   permission; for those five, the documentation must state the write scope the exception was granted
   against (`NGSIEM: WRITE`, `Identity Protection GraphQL: WRITE`, `MalQuery: WRITE`), so the write is the one the captain
   approved rather than a wider one discovered later.
   N3's execution tier must instead cite `Real time response: READ`: its exception is semantic execution authority, not permission to request another write scope.
2. **Corroborating behavioral evidence.**
   falcon-mcp's own treatment of that endpoint is the corroboration when falcon-mcp has a tool for it.
   When falcon-mcp has no tool for the operation, and only then, the corroboration is falconpy's generated
   endpoint table, which must map the exact operation id to the same method and route, plus PSFalcon, another
   first-party CrowdStrike SDK, wrapping the same operation.
   The registry records which form each operation uses in its required `evidence` field, and registry sealing
   rejects an entry whose second citation is neither a falcon-mcp `api_scopes.py` mapping nor that
   falconpy-plus-PSFalcon pair, including a pair whose falconpy mapping disagrees with the registered route.
   A neighbouring operation's falcon-mcp tool, or corroboration of the collection alone, remains insufficient.
   Corroboration alone admits no write scope or execution authority and reopens no excluded class.
   N3's explicit captain decision (§4.5), in addition to these citations, is required for its lifecycle operations.

### 2.3 The two-step query-then-hydrate pattern

Malware families use `QueryMalwareEntities` (`GET /intel/combined/malware/v1`) for a single combined list,
and `GetMalwareEntities` (`GET /intel/entities/malware/v1`) for one family slug's full record.
The list accepts raw FQL and binds offset continuation to the query context; §7.3 owns its limits.
Its minimal row is `id` (the family slug) and `family_name`.
The `family_name` column reads upstream `name`; the detail view preserves the upstream `name` field.
The detail view previews descriptions at 800 characters and offers `--full` only when truncated.
Both operations require `Malware Families (Falcon Intelligence):read`.
Identity policy rules use `get_policy_rules_query` then `get_policy_rules`, with hydration chunks of 100
and query order restored; the query supports `--name`, `--enabled true|false`, and `--simulation-mode true|false`.
It has no upstream limit, offset, or token parameter, so the command queries matching IDs once and hydrates them all.
The minimal row is `id`, `name`, `enabled`, and `simulation_mode` (from `simulationMode`).
`identity rule show <id>` returns the full rule, without applying its action.
These commands need `Identity Protection Policy Rules:read`, with no GraphQL permission.
Discover IoT uses `query_iot_hostsV2` followed by `get_iot_hosts`, restores query order after hydration,
and wraps `meta.pagination.after` in the existing token-model cursor; §7.3 owns its limits.
The minimal row is `id`, `hostname`, `device_type`, and `device_family`.
It requires the separate license-gated `Falcon Discover IoT:read` scope and accepts raw FQL.
All five commands have synthetic fixture and golden coverage; no tenant validation is claimed.
The deliberate discovery changes are the top-level help, unknown-command hint, identity subcommand hints,
and scope matrix.
Falcon MCP has no tools for these operations (its `falcon_mcp/modules/intel.py`, `idp.py`,
and `discover.py` were checked); evidence instead pairs the official
[Intel](https://developer.crowdstrike.com/api-reference/collections/intel/),
[Identity Protection](https://developer.crowdstrike.com/api-reference/collections/identity-protection/), and
[Discover](https://developer.crowdstrike.com/api-reference/collections/discover/) references with
falconpy's `_intel.py`, `_identity_protection.py`, and `_discover.py` endpoint tables, plus PSFalcon's
[`Get-FalconMalwareFamily`](https://github.com/CrowdStrike/psfalcon/blob/master/public/intel.ps1),
[`Get-FalconIdentityRule`](https://github.com/CrowdStrike/psfalcon/blob/master/public/identity-protection.ps1), and
[`Get-FalconAsset -IoT`](https://github.com/CrowdStrike/psfalcon/blob/master/public/discover.ps1).
The read-only enforcement and the two exception allowlists remain unchanged.

Intel actors and reports use combined entity queries for lists and entity endpoints for detail.
Each list accepts `--filter`, `--limit`, and `--cursor`; §7.3 owns the limits and §10.2 owns the row schema.
Lists preserve server order and total.
Their pagination contract is in §7.1 and §7.2.
An absent total is printed as unknown, with another page offered when the returned page fills the requested limit.
Detail requests `ids` and the documented `fields=__full__` collection, matches the requested id, and truncates top-level text fields at 800 characters unless `--full` is given.
An empty entity response or 404 is `NOT_FOUND`.
`actor show --mitre` additionally requests `GetMitreReport` with `actor_id` and `format=json`.
This returns a top-level JSON array; null or an empty array means no ATT&CK mappings.
The existing network sink parses that JSON even though falconpy labels the operation as a binary export.
No output file, CSV, PDF, or rule download is supported.

Evidence checked on 2026-10-18: the official [Intel collection](https://developer.crowdstrike.com/api-reference/collections/intel/) documents the five routes and scopes above, including JSON as a supported MITRE format.
[falcon-mcp modules/intel.py](https://github.com/CrowdStrike/falcon-mcp/blob/main/falcon_mcp/modules/intel.py) corroborates the two combined queries, limit/offset/filter parameters, and MITRE JSON array, and `common/api_scopes.py` maps their scopes.
falcon-mcp has no actor/report entity-detail tool; [falconpy's generated Intel table](https://github.com/CrowdStrike/falconpy/blob/main/src/falconpy/_endpoint/_intel.py) and [PSFalcon public/intel.ps1](https://github.com/CrowdStrike/psfalcon/blob/master/public/intel.ps1) (`Get-FalconActor`, `Get-FalconIntel`) corroborate entity ids and field collections.
These features match the SDK contracts and offline synthetic tests; they are not tenant-validated.

Falcon's query endpoints return **IDs**, and a second entity endpoint hydrates them into records.
falcon-mcp's `HostsModule.search_hosts` is the canonical shape: `QueryDevicesByFilter` for IDs, then
`PostDeviceDetailsV2` with those IDs.

Four consequences the design must carry:

1. **An ID-query-backed list costs two requests, not one.**
   Published in §13's cost table rather than hidden.
2. **The hydration step can lose the sort order.**
   falcon-mcp's `_reorder_by_ids` exists precisely because "some 'get entities by IDs' endpoints return
   resources in arbitrary order, discarding the sort".
   falcon-axi reapplies the query-step order after hydration, for the same reason and in the same place.
3. **The hydration step discards pagination metadata.**
   falcon-mcp's `_base_search_with_meta` docstring states it directly: hydration "discards
   `body.meta.pagination` from the query-step response, so callers that need `total`/`after` must capture it
   here".
   falcon-axi captures pagination from the query step before hydrating, because AXI §4's `count: N of M total`
   line depends on it.
4. **Hydrate batch caps are domain-specific and may differ from query caps.**
   Section 7.3 owns the query and hydrate limits for Alerts, Hosts, Discover accounts, and Data Protection configuration.
   falcon-axi chunks the hydrate step to the documented cap and never assumes the two numbers match.
   §7.3's default limits keep the common case inside one chunk.

Spotlight's combined endpoint returns entities directly, so `vuln list` uses one request per page and needs no
hydration.
NG-SIEM is a third shape again: a job, not a query.
`search start` creates one, `search status` polls it and carries the events once it reports `done`, and
`search stop` cancels it.
Each command defaults to one request; start and status optionally poll with `--wait` (§4.3).

## 3. Read-only posture and transport enforcement

### 3.1 What read-only means here, precisely

**v1 issues no request that changes any state in a Falcon tenant, apart from N1's search jobs (§4.3), N3's guarded RTR lifecycle (§4.5), and N4's bounded MalQuery searches (§4.6).**

The identity directory commands also send POSTs through a write-labelled scope (§4.4), but what they send is a fixed
query document that reads, so the request changes nothing; that distinction is the whole of captain
exception N2 and is held structurally rather than by assertion.

The naive formulation, "GET only", is wrong for Falcon, and this is the single most important place where a
sibling assumption fails to transfer.
The POST reads and their documented scopes are listed in §2.1.
falcon-mcp encodes the same fact in `_base_get_by_ids`, which takes a `use_params` flag choosing between "send
IDs as query parameters (GET)" and "send as request body (POST)" for what is the same read.

The converse also holds: a non-GET endpoint is not automatically safe, and neither is a read-scoped one.
`PatchEntitiesAlertsV3` is a PATCH and is obviously a write, but `RTR_InitSession` is scoped
`Real time response:read` and opens a session on a live endpoint (§4.1).

So the boundary is neither the HTTP verb nor the scope string.
**The boundary is the operation registry in §2.1, admitted by the two-citation rule in §2.2.**

### 3.2 Where the boundary sits, stated as rules

- No operation documented as `Scope <name>: WRITE` is registered, and no operation whose falcon-mcp scope
  mapping ends in `:write` is registered, **except the five ids the captain exceptions name**: `StartSearchV1`
  and `StopSearchV1` (N1), whose effect is `search-lifecycle` and whose only scope is `NGSIEM:write`, and
  `api_preempt_proxy_post_graphql` (N2), whose effect is `graphql-query` and whose only scope is
  `Identity Protection GraphQL:write`, plus `PostMalQueryExactSearchV1` and `PostMalQueryFuzzySearchV1` (N4), whose effect is `malquery-search` and whose only scope is `MalQuery:write`.
  No id outside the corresponding allowlist may carry either effect, and no other write scope is representable
  (§3.3 property 2).
- No operation that creates or changes server-side state is admitted outside N1, N3, and N4, **even when its scope is a read scope**.
  This rule still excludes scheduled-report launch and every RTR operation outside §4.5.
  N3 accepts sensor-mediated execution and session state only behind its own transport tier and guards.
  N1 accepts a different kind of server-side state, and the
  state in question is a query job in the caller's own tenant, which `search stop` can cancel and which
  touches no host, detection, policy, or configuration.
  N2 is not an exception to this rule, because no state is created: it is an exception to the scope rule
  above, accepted because the one endpoint Falcon serves identity reads from is scoped `WRITE` for reads, and
  the state-change risk it carries (GraphQL mutations) is closed off by the registry and not by the scope (§4.4).
- Ordinary authenticated commands write no local state.
  Local-write exceptions are owned by §12.2 (hook installation) and §4.5 (N3's journal and host locks).
  There is no token cache (§5.4), no credential
  file written by falcon-axi, no fixture recorder, no report downloads, and no output files.
- The registry is closed: adding a row requires both citations from §2.2 in the same change.

### 3.3 The transport is the enforcement point

Safety does not depend on command-layer discipline.
The scoped-operation transport accepts only a closed operation ID, resolves the canonical descriptor from the
frozen registry internally, and never accepts a caller-supplied descriptor, method, path, or URL.

```ts
// OperationId is the closed union defined in falcon_axi/transport/operations.py (§2.1).

type FalconOperation = Readonly<{
  id: OperationId;
  method: "GET" | "POST" | "DELETE";
  path: string;
  scopes: readonly string[];
  effect: Effect;  // closed union defined in falcon_axi/transport/operations.py
  evidence: Readonly<{
    docUrl: string;
    docScope: string;
    falconMcp: string;
  }>;
}>;

const SEARCH_LIFECYCLE_IDS: ReadonlySet<OperationId>;  // exactly StartSearchV1 and StopSearchV1
const GRAPHQL_QUERY_IDS: ReadonlySet<OperationId>;    // exactly api_preempt_proxy_post_graphql
const GRAPHQL_DOCUMENTS: Readonly<Record<string, GraphqlDocument>>;  // the only GraphQL text that can be sent
const OPERATIONS: Readonly<Record<OperationId, FalconOperation>>;

function request(id: OperationId, args: RequestArgs): Promise<FalconResponse>;
function requestOAuthToken(args: OAuthTokenArgs): Promise<OAuthTokenResponse>;
```

The sealed transport module exports only `request` and `requestOAuthToken`.
`requestOAuthToken` is a separately sealed authentication path with the fixed method `POST` and fixed path
`/oauth2/token`; it cannot issue a scoped operation and is subject to §6.3's trusted-origin policy.
It does not pass through `request`, because authentication is not one of the registered read operations.
Neither function exposes a raw URL, method, path, prepared request, low-level sender, or network primitive to
its callers.

The module's private `sendPermittedRequest` network sink accepts only a prepared request carrying a
module-local permit minted by one of those two entry points after its registry or OAuth checks pass.
The sink rejects a missing or invalid permit with `READ_ONLY_VIOLATION` before network access, so it cannot
send traffic the sealed entry points did not originate.

Six properties make this an enforcement mechanism rather than a convention, captain exception N1 added a
seventh, and captain exception N2 added an eighth:

Property 9 owns N3's extensions to the original N1/N2 transport; §19 records their implementation slices.
Property 10 owns N4's closed search body and sink checks.

1. **Deny by default, with runtime-immutable descriptors.**
   `request` takes an `OperationId` and resolves its descriptor from `OPERATIONS`.
   Registry construction copies every input, then recursively freezes each descriptor, its `scopes` array,
   its `evidence` object, and the outer record before any reference escapes.
   It verifies at runtime that the ID is an own key of the registry and that the resolved descriptor's `id`
   matches that key before sending anything; unknown or inconsistent values fail with
   `READ_ONLY_VIOLATION`.
   A caller cannot construct a descriptor that relabels an unregistered request as a read, and a retained
   mutable alias cannot change a canonical descriptor after initialization.
2. **`effect` is a closed union, with each exception closed by an id allowlist.**
   Writing `effect: "write"` does not compile.
   `effect: "search-lifecycle"` compiles, and registry construction then rejects it unless the descriptor's
   id is one of the two in `SEARCH_LIFECYCLE_IDS`, its documented scope matches `/:\s*WRITE$/i`, and its
   scope tuple is exactly `["NGSIEM:write"]`.
   `effect: "graphql-query"` is closed the same way: registry construction rejects it unless the descriptor's
   id is the one in `GRAPHQL_QUERY_IDS`, its documented scope matches `/:\s*WRITE$/i`, its scope tuple is
   exactly `["Identity Protection GraphQL:write"]`, and its method is POST.
   So neither exception can be reused for another operation or another write scope without editing its
   allowlist itself, which is a deliberate, reviewable diff that touches the transport, which is exactly
   where §1.6 says such a change would have to be argued.
   An id that one exception names cannot claim the other's effect, because each allowlist is checked against
   its own effect only.
   A `read` descriptor is rejected symmetrically if any of its scopes ends in `:write`, so a write scope
   cannot be smuggled in under the read tier either.
   Property 9 owns the fourth tier's exact tuple checks.
   N4 additionally seals `MALQUERY_SEARCH_IDS` to exactly `PostMalQueryExactSearchV1` and `PostMalQueryFuzzySearchV1`, with effect `malquery-search`, POST, each canonical route (§4.6), exactly `MalQuery:write`, and documented `MalQuery: WRITE`.
   Those ids cannot claim another effect, and no other id can claim this effect.
3. **The method is checked but not trusted.**
   Registry initialization rejects a descriptor whose method or path differs from the canonical values
   asserted by the registry-integrity test, and `request` draws no safety conclusion from the method being
   GET.
   This is how the enforcement stays honest under the semantic rule: the guarantee comes from the closed ID
   union, canonical registry, and evidence field, not from the verb.
   The permitted verbs are per tier: a `read` descriptor may be GET or POST, a `search-lifecycle`
   descriptor may be POST or DELETE, and a `graphql-query` or `malquery-search` descriptor must be POST.
   Property 9 owns N3's exact method and route restrictions, including its additional DELETE exception.
   That is a secondary defence, not the argument.
4. **Evidence is mandatory and machine-checked.**
   `evidence` is a required field.
   A test in the local required-check set walks `OPERATIONS` and fails verification if any entry has an empty
   `docUrl`, `docScope`, or `falconMcp`, if its second citation is neither falcon-mcp's `api_scopes.py` mapping
   nor the falconpy-plus-PSFalcon pair §2.2 accepts when falcon-mcp has no tool, or if `docScope` does not match the pattern its tier requires:
   `/:\s*READ$/i` for a `read` descriptor and `/:\s*WRITE$/i` for a `search-lifecycle`, `graphql-query`, or `malquery-search` one.
   That test is what stops a future contributor from adding an operation on assertion rather than on evidence,
   and it is the mechanical form of §2.2.
5. **A registry-integrity test asserts the whole surface.**
   `tests/offline/test_registry.py` asserts that `OPERATIONS` contains exactly the operations in §2.1;
   that the runtime keys
   equal the `OperationId` set; that each key, method, path, effect, scope, and evidence value equals its
   canonical expected value; that `SEARCH_LIFECYCLE_IDS` is exactly `StartSearchV1` and `StopSearchV1`, and
   `GRAPHQL_QUERY_IDS` is exactly `api_preempt_proxy_post_graphql`; and
   that no path matches a known-mutation route pattern (`/entities/*/action` or `/queries/*/action`).
   RTR route admission is separately sealed as described in property 9.
   The same test attempts to mutate every descriptor and nested value and asserts that the canonical values do
   not change.
   Changing the surface therefore requires changing the ID union, registry, and test in the same commit, on
   purpose.
6. **Exactly one private sink may use a network API.**
   `falcon_axi/transport/harness.py` is the sole file allowed to import a network API such as `falconpy`,
   `requests`, or `socket`, and its `send_permitted_request` function is the sole function allowed to reference
   or call those imports (`docs/design/v1-python.md` §3.2).
   The lint boundary rule permits imports only in that exact file and network references only in that exact
   function body, not elsewhere in the file or module, and rejects every network reference in every other
   function and file, including helpers in the sealed transport module.
   Indirect dispatch is denied too: process and shell execution APIs, including `subprocess`, are
   forbidden except at exact call sites on an explicitly reviewed allowlist whose entries fix the
   executable and argument pattern.
   Its entries are the fixed PowerShell DACL diagnostic in §12.1 and the fixed Python request worker in the network sink.
   The worker runs this same sink under the remaining invocation deadline, with request data on stdin rather than argv.
   Other shells and network-capable programs such as `curl`, `wget`, and `ssh` remain forbidden, and any change
   to the allowlist is reviewed as a transport-boundary change.
   An independent architecture test scans the source tree and import graph for both direct network references
   and process-execution bypasses.
   Both `request` and `requestOAuthToken` must pass a validated module-local permit to that sink, which rejects
   missing or invalid permits before network access.
   This closes direct and child-process network bypasses around both the registered-operation path and the
   sealed OAuth path and makes the sink the only place from which transport traffic can originate.
7. **A path variable is validated before a request is prepared.**
   The three NG-SIEM routes and the ThreatGraph process-summary route have `{name}` variables, and a variable is the
   only caller-supplied value that reaches a URL path, so a separator or a whole-value dot segment could
   retarget a request at a route the resolved descriptor never selected, defeating properties 1 and 5.
   `request` therefore checks that the supplied variable set is exactly the set the descriptor's path
   declares, failing `READ_ONLY_VIOLATION` when it is not, and rejects any value that is blank, contains
   `/`, `\`, or `%`, or is `.` or `..`, with `VALIDATION_ERROR`.
   ThreatGraph summaries additionally require the fixed `vertex_type=processes` value.
   falcon-mcp guards `repository` for the same reason and with the same rule; falcon-axi guards every
   variable of every route, because the search id is caller-supplied too.
   The offline `RecordedTransport` runs the same check, so the test seam is never more permissive than the
   sealed transport (§14.2).
8. **GraphQL text has one way in, and it is a closed registry of query documents.**
   The `graphql-query` operation takes the name of a registered document and its variables, never a body, and
   `request` builds the body itself from `GRAPHQL_DOCUMENTS` (`falcon_axi/transport/graphql.py`).
   Every other operation takes a body and never a document, so there is no path by which a caller-supplied
   string becomes GraphQL.
   Registry construction seals each document lexically: it must begin with `query`, contain exactly one
   top-level `query` operation, contain none of the words `mutation`, `subscription`, or `fragment` anywhere
   (not as an operation, a field name, or a fragment), contain no string literal and no comment, declare
   exactly the variables its text uses, and carry `:read` scopes only.
   The offline suite additionally parses every document with `graphql-core` (a dev-only dependency) and asserts
   one `query` operation whose root fields are within the allowlist `entities`, `timeline`, and `securityAssessment`.
   Variables travel only in the JSON `variables` object and are never interpolated into the text, which makes
   injection structurally impossible: falcon-mcp interpolates caller strings into GraphQL and leans on
   `sanitize_input`, and its timeline builder interpolates the entity id unsanitized.
   The network sink repeats the check as its last act before sending: a body for the GraphQL route that is not
   exactly a registered document, optionally with variables, is refused with `READ_ONLY_VIOLATION` even when
   it carries a valid permit.
   The offline `RecordedTransport` and the golden transport run the same body construction, so the test seam is
   never more permissive than the sealed transport.
9. **N3 requires a separate RTR execution tier and exact route exceptions.**
   Extend the effect union with `rtr-read-only-execute` and seal `RTR_EXECUTION_IDS` to exactly `RTR_InitSession`, `RTR_ExecuteCommand`, `RTR_CheckCommandStatus`, and `RTR_DeleteSession`.
   Each descriptor must cite `Real time response: READ`, carry exactly `Real time response:read`, and match its canonical method and route in §4.5.
   These four ids cannot claim `read`, `search-lifecycle`, or `graphql-query`, and no other id can claim the RTR execution effect.
   In particular, the new tier allows DELETE only for `RTR_DeleteSession`; N1's DELETE remains confined to `StopSearchV1`.
   The three passive history ids in §4.5 remain ordinary `read` descriptors, each with its own evidence.
   `RTR_HISTORY_ROUTES` in `falcon_axi/transport/operations.py` seals admission to the three passive history tuples in §4.5 during `_seal()`, including the separate audit collection.
   `RTR_EXECUTION_TUPLES` seals the four approved execution tuples separately, preserving the denial of every other RTR route and both action-route patterns.
   A collection prefix, a read scope, or a matching path without its exact id and method never grants access.
   Before minting a permit, the execution path checks the selected profile opt-in, the effective narrowed allowlist, the exact confirmation, the durable intent entry, and the READ_ONLY override.
   These checks authorize entry into one lifecycle; they never suppress deletion of an already opened session during cleanup.
   The prepared request binds one host, session, and command to that authorization; the sink repeats the operation and command checks before any send, as it does for N2's document check.
   Cleanup authority is confined to deleting that run's session and cannot be used to execute again or delete an unrelated session.
   The recorded and golden transports must enforce the same checks.
   Registry and sink tests must refuse every excluded operation, mismatched tuple, widened profile list, disallowed command form, and unchecked body, even with a broader credential or a forged prepared request.

10. **N4 admits only validated literal patterns and bounded matches.**
    The MalQuery tier reconstructs a body containing only `patterns` and `options.limit`.
    Each pattern has exactly `type` and `value`; only one ASCII and one literal hex pattern are admitted, and the result limit is an integer from 1 to 100.
    The same validator runs at preparation in real and recorded transports and again at the sink, including bounded workers.
    Search requests admit no query parameters or path variables.
    A forged permitted request with YARA, extra options, invalid patterns, or an unbounded limit fails `READ_ONLY_VIOLATION` before sending.
    Neither search POST is automatically replayed after any response or ambiguous network failure.

The registered-operation shape is borrowed from `awx-axi`, whose read-only enforcement also lives at the transport
seam with the reasoning that "a document that only *says* read-only is one forgetful contributor away from
being wrong".
The adaptation is that `awx-axi` can key on the HTTP verb and falcon-axi cannot.

### 3.4 Read-only is not the same as invisible

An authenticated read still sends requests against the tenant.
Every authenticated falcon-axi invocation mints an OAuth2 token against the tenant, while authentication-free
`scopes`, `setup`, and unresolved `auth status` invocations do not (§5.6).
falcon-mcp sets an RFC-shaped User-Agent (`get_user_agent`), and falcon-axi likewise identifies authenticated
traffic as `falcon-axi/<version> (Python/<version>; <platform>)`.
For the audit-visibility evidence limitation, see §17.13.
This is stated because "read-only" means no mutation, not no authenticated traffic.

## 4. The mutation surface and the closed captain exceptions

§1.5 lists the excluded classes.
This section records the exclusions that needed an argument and the four captain decisions that narrowly reversed them.

### 4.1 Real Time Response stays excluded except for N3

falcon-mcp's `rtr` module registers `init_rtr_session`, `pulse_rtr_session`, `execute_rtr_read_only_command`,
`run_rtr_read_only_command_and_wait`, `check_rtr_command_status`, `list_rtr_session_files`, and
`delete_rtr_session`, and describes itself as "read-only RTR triage workflows".

RTR execution is not a passive read in the sense Invariant R means.
`RTR_InitSession` opens a live session **on a production endpoint** through the sensor; falcon-mcp annotates
it `readOnlyHint=False, idempotentHint=False`.
`RTR_ExecuteCommand` runs a command on that endpoint.
Both are mapped to the scope `Real time response:read` in falcon-mcp's `api_scopes.py`, which makes the scope
string actively misleading as a safety signal and is precisely why §3.1 refuses to use scope names as the test.

Blast radius: sensor-mediated execution on a live host and a session that must be torn down or lingers.
CrowdStrike enforces the read-only command boundary; N3 requires falcon-axi to narrow it again with its own allowlist check before any send.
Permission to hold `Real time response:read` alone is never permission to execute through falcon-axi.

Note that `RTRAuditSessions` and `RTR_ListAllSessions` are genuinely passive reads of RTR *history*.
The captain has admitted those history reads, with `RTR_ListSessions` for hydration, as ordinary read commands through §2.2's two-citation rule.
The captain also granted N3's guarded `rtr run` lifecycle (§4.5), not the rest of the RTR collection.
Admin and active-responder commands, file get or put, scripts, batch sessions, and pulse are excluded.
The four admitted lifecycle operations need no pulse within one bounded run; a future need for pulse requires another explicit decision rather than widening N3 implicitly.

### 4.2 Scheduled reports are excluded, despite a read scope

falcon-mcp registers `launch_scheduled_report` and `download_report_execution`, both under
`Scheduled Reports:read`.
Launching creates a server-side execution and can deliver output to configured recipients; downloading writes
a file outside falcon-axi's config directory.
Both fail §3.2's "no operation that creates or changes server-side state, even when its scope is a read scope"
rule.

### 4.3 NG-SIEM search was excluded on the credential-scope test, and captain exception N1 reversed it

`StartSearchV1` and `StopSearchV1` map to **`NGSIEM:write`** in falcon-mcp's `api_scopes.py` and are
documented `Scope NGSIEM: WRITE`; `GetSearchStatusV1` is `NGSIEM:read`.
The original exclusion was the cleanest of the three: under §5.7 falcon-axi's provisioning documentation asked
for read scopes only, so an operation requiring a write scope could not be provisioned at all.
It needed no judgment about side effects, only the scope name.

**The captain granted exception N1, admitting exactly the three search lifecycle operations and no other
NG-SIEM capability.**
The decision is the captain's; what this section owes is the boundary, so the exception cannot drift.

What N1 admits:

- `StartSearchV1`, `GetSearchStatusV1`, and `StopSearchV1`, and nothing else in the NGSIEM collection.
- One write scope, `NGSIEM:write`, required by start, stop, and the fixed searches `identity activity` and `host usb`.
  Their help states this command-specific requirement without claiming it is falcon-axi's only write scope;
  N2 additionally requires `Identity Protection GraphQL:write` for identity reads (§4.4).

What N1 does **not** admit, and §1.5 still excludes:

- Event ingest, lookup-file upload or deletion, parser create, update, install, or delete, dashboard writes,
  saved-query writes, and correlation-rule writes, all also `NGSIEM:write`.
- Charlotte AI and the AgentWorks collection, which is a separate scope and a separate product surface.
- Every other class in §1.5: RTR beyond N3, containment, detection-status change, policy, IOC, IOA, exclusion,
  quarantine, host-group, user, Flight Control, scheduled-report, Shield, and suppression writes.

Why the state N1 creates is the state the captain was willing to accept, stated so a reviewer can check the
reasoning rather than trust it:

- The state is a query job in the caller's own tenant. It reads event data and writes none.
- It touches no host, no sensor, no detection, no policy, and no configuration, so its blast radius is the
  job itself and the query cost it incurs.
- It is reversible by the same surface: `search stop` cancels a job, which is why N1 admits stop rather than
  leaving a started job unabandonable. A search command set without `StopSearchV1` would be strictly less
  safe than one with it.
- Unlike `RTR_InitSession` (§4.1), nothing is executed on an endpoint, and unlike a scheduled report (§4.2)
  nothing is delivered to a recipient or written to disk.

How the boundary is held rather than asserted: §3.3 property 2 confines the `search-lifecycle` effect to an
id allowlist of exactly those two ids with exactly that one scope, so admitting a third NG-SIEM write means
editing the allowlist in the transport, which is the reviewable diff §1.6 requires.

The surface itself is three commands, because an NG-SIEM search is a job rather than a query:

| Command | Operation | Scope | What it does |
| --- | --- | --- | --- |
| `search start --query <CQL> [--wait <seconds>]` | `StartSearchV1`, optionally `GetSearchStatusV1` | `NGSIEM:write`, optionally `NGSIEM:read` | Creates one job; optionally waits for its events |
| `search status <id> [--wait <seconds>]` | `GetSearchStatusV1` | `NGSIEM:read` | Running, cancelled, or done with its events; optionally waits |
| `search stop <id>` | `StopSearchV1` | `NGSIEM:write` | Cancels one job |

Three design consequences, each of which is a deliberate departure from the read domains:

1. **Polling is optional and bounded.**
   Start and status accept `--wait <seconds>`, an integer from 1 to 50, to fit remote runners with short call budgets.
   Without it, start returns the identifier and status makes one request, preserving the recorded output contract.
   With it, status polls immediately and then at one-second intervals against a monotonic deadline, stopping on done or cancelled.
   One deadline begins at command entry and includes authentication, job creation, polling, in-flight request time, and retry sleeps.
   Each request timeout and Retry-After sleep is capped to the remaining budget, and no request begins after the deadline.
   Deadline-bound network exchanges run in a short-lived Python worker that is killed and reaped on expiry, bounding response consumption even when bytes keep arriving.
   The worker checks the same absolute monotonic deadline before sending; requests without a deadline stay in-process.
   Once a job identifier is available, expiry returns the existing running output with that id and a `search status <id> --wait 30` follow-up that preserves the repository.
   Expiry during authentication or creation before an identifier is received returns `NETWORK_UNREACHABLE` instead.
   With `--wait`, polling errors retain their error code and details and add the job id, repository, and status and stop recovery commands.
   Without `--wait`, status errors preserve the recorded output contract without recovery enrichment.
   Expiry never cancels the job.
   The search help goldens deliberately gain wait and timestamp guidance; the scopes golden adds start to NGSIEM:read because optional waiting reads status.
2. **There is no `--limit` and no `--cursor`.**
   A query job carries no `meta.pagination` (§7.1), so neither pagination model applies and neither is
   invented. The result set is bounded in the query itself, with `| head(N)` or an aggregate, which is where
   CQL puts it.
   Event `@timestamp` values are epoch milliseconds; readable UTC times belong in CQL using `| formatTime("%Y-%m-%dT%H:%M:%SZ", field=@timestamp, as=time, timezone="UTC")`, with no client-side formatting flag.
3. **A rejected search is answered in CQL terms, not FQL terms.**
   §9.4's 400 translation looks for the words `fql`, `filter`, and `query` to decide it was a filter problem,
   and an NG-SIEM rejection would trip that and offer FQL advice for a language that is not FQL. The search
   domain therefore translates its own 400 and 404 before that rule sees them.

`--repository` defaults to `search-all`, the view spanning every repository, which is also falcon-mcp's
default; it is a path variable, so §3.3 property 7 validates it.

#### `identity activity`: a fixed search, not a fourth operation

`identity activity <account> [--since <window>]` composes one CQL query and sends it through the same
`StartSearchV1` request `search start` makes.
It registers no operation, needs no scope beyond `NGSIEM:write`, and leaves the `SEARCH_LIFECYCLE_IDS`
allowlist untouched, so it is inside N1 rather than an extension of it.
It exists because the event-name families, the join fields, and the projection are knowledge an agent would
otherwise re-derive each session:

- The query matches `#event_simpleName` against `ActiveDirectory*`, `Sso*`, and `IdpEntityRiskScoreChange`,
  joins on `SourceAccountObjectGuid`, `PerformedOnAccountObjectGuid`, and `AccountObjectGuid` for a GUID or on
  `SourceAccountSamAccountName`, `SourceAccountUserName`, `PerformedOnAccountName`, and `SamAccountName` for a
  name or UPN, and projects ten columns newest first with `limit=200`.
  The projection omits the `KerberosResponseTicketHashSample` fields authentication events carry.
- A detection's `account_id` (`source_account_object_guid`) equals NG-SIEM's `SourceAccountObjectGuid`, which is
  what makes `detection show` to `identity activity` a one-step pivot (verified live, §18).
- The account is spliced into CQL text, so it is validated against a closed shape (a hyphenated GUID, or
  1-256 ASCII letters, digits, and `. _ @ $ -`) and refused otherwise, before any request.
  No wildcard is accepted.
- Both forms match through an anchored case-insensitive regex, `/^value$/i`, because a quoted CQL string
  compares case-sensitively and Falcon stores GUIDs in upper case (verified live, §18); names escape `.` and
  `$`.
- The repository is fixed to `search-all`; `--since` defaults to `24h` and accepts the same relative windows
  as `search start`.
  Polling and cancelling stay `search status` and `search stop`, with optional bounded polling on status.
- Detection pivots and job suggestions follow §7.2's shared suggestion-context contract.
  Both GUID and name pivots are shell-quoted so the suggested command preserves the literal subject.

#### `host usb`: Device Control activity as a fixed search

Device Control policy reads shipped in P6; P7 delivers USB activity with `host usb <device id> [--since <window>]`.
USB activity has no REST endpoint and is read from NG-SIEM sensor events through the existing `start_search` path inside N1.
It adds no operation or scope and leaves `SEARCH_LIFECYCLE_IDS` unchanged.
The AID must be exactly 32 ASCII hexadecimal characters, validated before authentication and normalized to lowercase in CQL.
The fixed query filters `#event_simpleName=/^(DcUsbDeviceConnected|DcUsbDeviceDisconnected|DcUsbDevicePolicyViolation)$/ aid=<aid>` and projects `@timestamp, #event_simpleName, ComputerName, DeviceManufacturer, DeviceProduct, DevicePropertyDeviceDescription, DeviceUsbClass, DcPolicyAction, event_platform` with `table(..., limit=200, sortby=@timestamp, order=desc)`.
The event kind distinguishes connections, disconnections, and policy violations even when the device fields match.
The event and field names come from CrowdStrike's [USB Device Control Activity dashboard](https://github.com/CrowdStrike/logscale-community-content/blob/0152b8a/Log-Sources/CrowdStrike/FLTR/crowdstrike-fltrdevicecontrol/src/dashboards/USBDeviceControlActivity.yaml), not the login-gated event dictionary, and are not live-verified.
The query projects available event fields directly, without the dashboard's saved-query hostname enrichment, interface-descriptor join, or display-value mappings.
The repository is fixed to `search-all`, and `--since` defaults to `24h` using the same relative windows as `search start`.
Starting costs one token request and one `StartSearchV1` request, requires `NGSIEM:write`, and returns the existing search-start output with `search status` and `search stop` suggestions.
Polling stays in `search status`, including its bounded `--wait` support, and requires `NGSIEM:read`.
An empty result can mean no USB events or no Device Control licence; help states both because NG-SIEM cannot distinguish them.
Only synthetic offline responses are used for verification.
The new command reference deliberately expands the help and scope golden templates and the `unknown-host-subcommand` document's valid-subcommand list; existing domain output stays unchanged.

### 4.4 The Identity Protection directory was excluded on the credential-scope test, and captain exception N2 reversed it

Identity Protection serves its directory and activity timeline through one GraphQL endpoint,
`POST /identity-protection/combined/graphql/v1` (`api_preempt_proxy_post_graphql`), documented
`Scope Identity Protection GraphQL: WRITE`.
That scope is required for reads: CrowdStrike's Tech Hub states that "the endpoint requires the `:write` scope
even when your query only reads data", every read-only consumer found asks for it, and falcon-mcp's
`api_scopes.py` maps the id to it beside four `:read` scopes.
The same endpoint also accepts mutations; falconpy's description is "Allows to retrieve entities, timeline
activities, identity-based incidents and security assessment. Allows to perform actions on entities and
identity-based incidents."
So it failed §2.2 and §3.2 on the scope test alone, exactly as `StartSearchV1` did, and for the same reason it
could not be provisioned under a read-only §5.7.

**The captain granted exception N2, admitting `api_preempt_proxy_post_graphql` for fixed read-only query
documents and nothing else.**
N2 is **not general write authority**: it admits one write-labelled scope for the purpose of reading, and it is
neither a precedent for admitting another write scope nor a licence to send any GraphQL a caller supplies.

What N2 admits:

- One operation, `api_preempt_proxy_post_graphql`, and one write-labelled scope, `Identity Protection
  GraphQL:write`.
- Only the query documents in the closed registry of §3.3 property 8: the entity directory (`entities`, filtered
  by name, email, domain, type, or id), one entity's detail (risk, risk factors, accounts, associations, open
  incidents), the activity timeline (`timeline`), and security assessment (`securityAssessment`).
- The domain read scopes those documents need, `Identity Protection Entities:read` and
  `Identity Protection Timeline:read`, plus `Identity Protection Assessment:read`, which are ordinary read scopes.

What N2 does **not** admit, and §1.5 still excludes:

- Any GraphQL `mutation` or `subscription`, any act on an entity or identity incident, and any watchlist, state,
  assignment, or comment change.
- Any raw GraphQL passthrough: no `--query`, no `--document`, no stdin, no environment variable, no config key.
- `Identity Protection Entities:write`, `Detections:write`, `Policy Rules:write`, and Automation scopes; policy
  rule creation or deletion; and every account action (password reset, forced password change, MFA
  enforcement, account disable, session revocation, block).
- The standalone GraphQL `incidents` document, which is absent.
- Every other class in §1.5.

Why the exception is safe to grant, stated so a reviewer can check the reasoning rather than trust it.
Unlike N1, falcon-axi's *behavior* stays read-only: no job, session, or record is created, so there is no state
to cancel.
What changes is the **credential**: a client holding `Identity Protection GraphQL:write` could send mutations
through this endpoint if something let it.
The boundary is therefore on what falcon-axi sends, not on what the scope permits:

- §3.3 property 2 confines the `graphql-query` effect to one id with exactly one scope, so a second write scope
  or a second GraphQL operation means editing the allowlist, which is the reviewable diff §1.6 requires.
- §3.3 property 8 gives GraphQL text exactly one way in, a closed registry of documents proven lexically and
  by a parser to be single `query` operations, with variables only ever in the JSON `variables` object.
- Each document carries its own domain read scope, so `scopes` prints a per-command matrix and a 403 names
  both the write-labelled scope and the read scope that command needs.
- §15.1's live boundary is restated for it.

A mutation would also appear to need a per-domain write scope beyond `GraphQL:write` (a third-party connector
documents `Detections: WRITE` for incident updates), which would make a client provisioned as §5.7 describes
unable to mutate even through a hypothetical bypass.
That is third-party and unverified, and verifying it would mean sending a mutation, which falcon-axi does not
do; this document does not rely on it.

The GraphQL surface is four commands, each one request:

| Command | Document | Scopes | What it does |
| --- | --- | --- | --- |
| `identity list` | `identity_list`, `identity_list_users`, `identity_list_endpoints` | `GraphQL:write`, `Entities:read` | One directory page, filtered by `--name`, `--email`, `--domain`, `--type` |
| `identity show <id>` | `identity_show` | `GraphQL:write`, `Entities:read` | One entity's detail |
| `identity timeline <id>` | `identity_timeline` | `GraphQL:write`, `Timeline:read` | One page of an entity's activity, newest first, from `--since` and optionally `--category` |
| `identity assessment [--domain <name>]` | `identity_assessment` | `GraphQL:write`, `Assessment:read` | Overall security score, level, and risk factors, optionally for one configured domain |

The assessment selection matches CrowdStrike's [PSFalcon security assessment sample](https://github.com/CrowdStrike/psfalcon/blob/master/samples/identity-protection/security-assessment-for-domain.ps1): `securityAssessment(domain:)` with `overallScore`, `overallScoreLevel`, and `assessmentFactors { riskFactorType severity likelihood }`.
Falcon-mcp's `falcon_mcp/modules/idp.py` supplies no assessment document; its `common/api_scopes.py` corroborates `Identity Protection Assessment:read`.
The domain is an optional `String` variable and never interpolated into document text.
Output is an `assessment` object with `score`, `level`, and `factors` rows (`type`, `severity`, `likelihood`), plus `domain` when supplied.
A null assessment prints `0 security assessments`; GraphQL errors remain errors.
This document is tested offline against a synthetic schema, not tenant-validated.

Sensor inventory uses ordinary read-tier REST operations rather than N2.
The [official Identity Protection reference](https://developer.crowdstrike.com/api-reference/collections/identity-protection/) documents `QuerySensorsByFilter` and `GetSensorDetails` with `Identity Protection Entities: READ` and supplies the sensor response field names.
Falcon-mcp `falcon_mcp/modules/idp.py` has no sensor tool; falconpy `_endpoint/_identity_protection.py` maps their exact IDs, methods, and routes, and PSFalcon `public/identity-protection.ps1` `Get-FalconIdentityHost` wraps both operations.
`identity sensor list [--filter <FQL>] [--limit N] [--cursor <token>]` queries IDs, captures total, hydrates them, and reapplies query order.
Its page bounds are owned by §7.3, and its authenticated offset cursor binds filter, credential, origin, and selected tenant.
Rows contain `device_id`, `hostname`, `status`, and `agent_version`.
`identity sensor show <device_id>` hydrates one ID and adds the documented heartbeat, policy, auditing, and status-cause fields when present.
An absent sensor is `NOT_FOUND`; an empty list skips hydration.
These commands have offline coverage and have not been tenant-validated.

Five design consequences:

1. **Three list documents, not one with a type variable.**
   `--type user|endpoint` selects between documents whose `types:` argument is a literal enum (`[USER]`,
   `[ENDPOINT]`), because falcon-mcp's queries prove the enum values but nothing in the evidence names the
   GraphQL type of a `$types` variable, and a wrong variable type would fail validation of every list call.
   The same discipline governs every document: the argument and field names come from falcon-mcp and
   CrowdStrike's own queries, and the variable types (`UUID`, `Cursor`, `DateTimeInput`,
   `TimelineEventCategory`, `String`, `Int`) from CrowdStrike's and falconpy's published samples.
2. **Pagination is Relay `first`/`after`, behind the same `--cursor`.**
   The token carries the GraphQL `endCursor`, bound to the operation, the filters, the region, the tenant
   selection, and the credential like every other cursor (§7.2).
   The directory's `(type, name, email, domain)` tuple is serialized as JSON before fingerprinting, so
   delimiters inside a filter cannot move text between fields.
   A timeline cursor also carries the window start, so a later page continues the window the first page used
   rather than one shifted by the time between calls.
   `--limit` is capped at 200, which is falcon-mcp's cap: CrowdStrike publishes no ceiling for this endpoint.
3. **An entity id is a GUID.**
   `identity show` and `identity timeline` validate it as one before any request, because the variable's GraphQL
   type is `UUID`.
   Credential-independent identity inputs are validated during parsing, before credential resolution or
   OAuth token minting: directory type, name, email, and domain; detail and timeline GUIDs; and timeline
   category and relative window.
   `--help` remains authentication-free and bypasses these value checks.
   For an Active Directory user the id appears to be the account object GUID (an identity detection's
   `source_account_object_guid`), which is third-party evidence subject to §17.15's limitation.
4. **A GraphQL failure on HTTP 200 is an error.**
   GraphQL reports an execution failure as a body `errors` list, so these commands inspect the body on success
   and fail with `UPSTREAM_ERROR` when `errors` is non-empty or `data` is not an object, never rendering it as
   an empty result (see §17.9 for the separate REST decision).
   A 400 is also `UPSTREAM_ERROR` and never `FQL_INVALID`: GraphQL validation messages say "query" and "field",
   which §9.4's FQL rule would mistake for a filter problem, and falcon-axi's documents are fixed, so a
   rejection means the document does not match the tenant's schema.
5. **The schema is not public, and the console's is not the API's.**
   A field valid in the console's GraphQL editor has returned HTTP 400 from the API endpoint (PSFalcon issue
   #464), so a document must be validated against the API, never the console.
   The offline suite proves their shape and safety, not their fit to the live schema; §17.14 owns the source-parity closure.

Operator grant steps are owned by the README's API client permissions section and reflected in each
identity command's `SCOPE_DENIED` remedy.

### 4.5 RTR was excluded on semantic execution grounds, and captain exception N3 narrowly reverses it

**The captain granted exception N3 so that an API client permitted to start an RTR session and run the standard read-only commands can do so through falcon-axi.**
The captain also admitted passive RTR history reads.
Passive RTR history ships in slice R1 (§19).
R2 implements the internal execution tier, profile extension, lifecycle core, and journal writer.
R3 exposes `rtr run` with local preview and exact host/command execution confirmation.
The README's generated reference continues to own the shipped surface.

What N3 admits:

- Passive history reads using `RTR_ListAllSessions` and `RTRAuditSessions`, with `RTR_ListSessions` as the session metadata hydrate, through §2.2 as ordinary reads.
  They never initialize, pulse, execute, or delete a session and do not need execution opt-in or confirmation.
  Query pagination metadata and ordering survive hydration as in §2.3; audit returns combined records without that hydrate.
- One guarded lifecycle command, `rtr run`, using only `RTR_InitSession`, `RTR_ExecuteCommand`, `RTR_CheckCommandStatus`, and `RTR_DeleteSession`.
  It runs one command on one explicitly identified host and owns the complete session lifecycle in the same invocation.
- The closed command set `cat`, `cd`, `csrutil`, `env`, `eventlog`, `filehash`, `getsid`, `ifconfig`, `ipconfig`, `ls`, `mount`, `netstat`, `ps`, `reg query`, and `users`.
  This is CrowdStrike's read-only responder set restricted to what the command API accepts, with `eventlog` limited to view/list forms.
  `help`, `clear` and `history` are excluded because they are builtins of the interactive console, and the command API rejects them as `Command not found` on every tested platform.
  Availability is per platform, because Falcon also answers a command that the host's platform lacks with `Command not found`.
  Each command was run once through the command API on one Windows and one Linux host:
  `cat`, `cd`, `env`, `filehash`, `ls`, `mount`, `netstat` and `ps` ran on both;
  `eventlog`, `getsid`, `ipconfig` and `reg query` ran only on Windows;
  `ifconfig` and `users` ran only on Linux;
  and `csrutil`, a macOS command, ran on neither, and macOS was not tested.
  `COMMAND_PLATFORMS` in `falcon_axi/rtr_policy.py` records this and generates the help text and the skill guidance.
  Excluding `eventlog` backup/export is the one deliberate narrowing for falcon-axi's semantic read-only invariant because those forms write files on the host.
  This list is fixed by this decision, not discovered dynamically from the server or widened when an SDK gains commands.
  A profile may narrow it and never widen it.

What N3 does **not** admit:

- Admin or active-responder operations, file get or put, scripts, batch sessions, offline queueing, detached execution, or caller-selected existing sessions.
- Any other RTR operation, including aggregates, session-file reads, extracted-file downloads, queued-session operations, and pulse.
  One bounded run must fit without pulse; there is no background keepalive or persistent session surface.
- Any registry bypass, arbitrary Falcon operation, raw request body, shell passthrough, or profile-supplied extension to the command allowlist.
- Any other excluded capability class in §1.5 or any additional write-labelled scope.

The blast radius remains sensor-mediated execution on a live host.
Calling the commands read-only does not make session creation or command activity passive.
CrowdStrike enforces its read-only boundary and falcon-axi must independently narrow that boundary before any send.
The permission scope alone proves neither safety nor authorization to run.

Its `reg query` form corroborates why admitting the entire `reg` family would be too broad.
These are source checks only, with no tenant-validation claim.

#### Guards, lifecycle, output, and journal

1. **Off by default, with an explicit profile opt-in.**
   The strict profile schema (§12.1) includes this capability; absent or disabled opt-in refuses execution before authentication.
   The environment credential profile alone never opts in, and no invocation flag substitutes for profile opt-in.
   An optional profile command restriction is a subset of the fixed list above; an unknown or wider entry is `CONFIG_INVALID`, not silently accepted.
   `FALCON_AXI_READ_ONLY` is checked before token minting and always defeats profile opt-in, `--execute`, and `--confirm`.
   Passive history reads remain permitted by READ_ONLY.
2. **Every run previews, with exact noninteractive confirmation.**
   The shipped surface is `rtr run <device_id> --command '<complete command>'`.
   Without `--execute`, it prints a local TOON preview and makes no network request.
   The preview identifies the host, exact command including arguments, effective profile restriction, execution deadline, output cap, journal destination, and mandatory session deletion.
   Execution requires both `--execute` and `--confirm '<device_id>:<complete command>'`, matching the validated host and complete command byte for byte.
   Missing or mismatched confirmation is a usage error before authentication; neither a wildcard nor a generic yes is accepted.
   A confirmed invocation emits the same preview before session creation.
   Redaction applies to previews and suggestions; a sensitive value is never restored merely to print a confirmation hint.
3. **One command grammar, checked again at the transport boundary.**
   Parse the full command once and bind it to the preview and authorization rather than trusting a caller-supplied `base_command` separately from `command_string`.
   Match whole command tokens, never prefixes; `reg` is admitted only with the `query` subcommand, never `set`, `delete`, `load`, or `unload`.
   `eventlog` admits only view/list forms; backup/export are excluded because they write files on the host.
   Reject compound commands, separators, redirection, embedded newlines, and script or shell substitution forms; paths and arguments are RTR data, never passed to a local shell.
   Literal parentheses are permitted inside quoted data arguments, including Windows paths under `Program Files (x86)`; substitution and other execution syntax remain rejected even inside quotes.
   The allowlist and full-form validation run before any execution-tier send, and the sink verifies that the sent body matches the authorized command and host/session context (§3.3 property 9).
4. **Initialize, execute once, poll within a bound, ALWAYS delete.**
   The lifecycle is `RTR_InitSession -> RTR_ExecuteCommand -> bounded RTR_CheckCommandStatus -> RTR_DeleteSession`.
   No session id is accepted as input and no command hands a session off for later use.
   Set finite deadlines for authentication, initialization, execution and polling, and reserve a separate finite cleanup budget that remains available after the execution deadline expires.
   Request timeouts, retries, polling sleeps, output chunks and response consumption must all respect those bounds, following the deadline mechanism used by N1 rather than an unbounded read loop.
   Do not queue work for an offline host.
   Never blindly replay init or execute after an ambiguous send, because it may create another session or run the command twice (§7.4).
   Once a session is known, deletion runs in unconditional cleanup on success, error, timeout, output-cap exhaustion, and catchable interrupt, with cancellation deferred while cleanup runs.
   No session may deliberately linger, and cleanup failure is never reported as success.
   A network partition, lost init response, or uncatchable process termination can prevent proof of deletion; surface and durably journal cleanup as failed or unknown rather than claiming the session is gone.
   The R2 ownership and recovery contract below governs those cases; an unreachable API cannot prove remote deletion.
5. **Bounded output and a redacted durable journal are mandatory.**
   R2 fixes finite byte, chunk, and time limits before R3 can ship, with no unlimited-output escape hatch.
   Cap acquisition as well as rendering; retain a bounded preview with explicit truncation or incomplete status instead of silently discarding the distinction.
   Render output as quoted, untrusted TOON data and apply §5.5 redaction before preview truncation.
   Before init, append and durably flush a redacted intent record to `FALCON_AXI_WRITE_LOG` or the state-dir `writes.log` (§5.2).
   Refuse execution if that record cannot be made durable.
   Record timestamp, run correlation, redacted target and command, authorization decision, phase reached, command outcome, and cleanup outcome, without credentials, standalone CIDs, or raw command output.
   Append and flush the outcome on every exit path; an outcome-write failure still triggers deletion and makes the run fail explicitly.
   Use private local files, reject unsafe journal targets, and allow no journal-disable switch.
   `scripts/architecture_check.py` enforces this narrow local-write exception alongside hook installation; it grants no general file-write authority.

#### R2 execution limits and ownership recovery

The internal core uses a 50-second shared authentication/init/execute/status deadline and a separate 10-second deletion budget.
Init and execute are attempted once, with no transport replay, including after a 429; status and delete also receive no automatic replay.
Acquisition is limited to 1 MiB of decompressed response bytes per execution-tier request and at most 64 status requests.
Status polling carries the validated nonnegative response sequence into the next request, independently of the request-count limit.
Falcon omits the sequence from the final response of a completed command, so only a response with `complete: true` may lack it, and it then repeats the requested sequence; an incomplete response without a valid sequence still fails.
Retained command output is capped at 64 KiB, with redaction applied across accumulated chunks before preview truncation.
Reaching either output limit returns explicit incomplete/truncated output after deletion; errors carry the bounded output and cleanup outcome.
A `Command not found` rejection from Falcon on submission is reported as `UPSTREAM_ERROR` naming only the allowlisted base command, never the full command string, and the session is still deleted.
Commands are limited to 4096 UTF-8 bytes and one 32-hex-character device id.
Profile settings are `rtr: {"enabled": true, "commands": ["ps", "reg query"]}`; `commands` is optional and can only narrow the fixed set, including to the empty set.
The environment credential profile cannot opt in.

The journal's intent, pre-init, known-session, and final records share a unique run correlation.
The pre-init record is flushed before sending and records cleanup as unknown, so a lost init response or process death never appears as proof that no session exists.
A known session id is retained in the durable record before execute; deletion is attempted even if that record cannot be flushed.
CrowdStrike init retrieves the calling user's existing session on the host when one exists, so its returned session is not invocation-exclusive ([official init reference](https://developer.crowdstrike.com/api-reference/collections/real-time-response/#rtr-initsession)).
The core holds an exclusive nonblocking OS file lock per host in falcon-axi's state directory from before authentication through init, execute, polling, deletion, and final journaling.
A second local run using that state directory refuses before any request; lock files remain empty and are retained to preserve the shared lock inode.
Runs from other machines using the same API client can still share the session, which CrowdStrike does not let a client prevent; operators must avoid such overlap.
Only the session returned by this run's init receives cleanup authority, including after READ_ONLY is enabled during execution.
The core never accepts a caller-selected session, discovers sessions, or starts another init to recover a missing id.
After an ambiguous init or failed deletion, the operator must reconcile the target's sessions in the Falcon console using the run's timestamp, target, and known session id when available, and close any remaining session before initiating another run.
This is manual recovery, not a claim that an unreachable API proves deletion; there is no automatic rerun or background cleanup.
Uncatchable termination leaves the last durable phase as the recovery evidence.
If final journaling fails, the returned error retains the run correlation, bounded output, cleanup outcome, and journal error alongside any lifecycle error.
A deletion or final journal failure fails the run without changing the known command completion status; cleanup and journal failures are reported separately from command completion.
Initialization errors retain their actionable code, guidance, and details alongside the run correlation and conservative cleanup-unknown recovery information.

Only `rtr_journal.py` may create journal and lock directories and files and append/fsync journal records, using descriptor-relative no-symlink traversal and refusing unsafe ownership or permissions, hard links, and special files.
Every ancestor must be owned by root or the current user and prohibit group/world writes unless its sticky bit protects child entries.
Final directories must be owned by the current user and prohibit group/world writes; files must additionally prohibit all group/world access.
The writer fails closed on platforms without the POSIX private-file primitives; R3 execution supports POSIX only and portable private creation remains unverified.
The CLI flushes the redacted preview before authentication and turns SIGINT/SIGTERM into lifecycle failures whose cleanup and journaling finish before structured error output.
Region and tenant flags select the same cloud and child tenant for the entire lifecycle; unknown origins remain refused even with `--allow-unknown-origin`.
Trusted region URLs are canonicalized to lowercase hostnames without a trailing slash before preview and authentication.
Raw command output is never journaled.

### 4.6 MalQuery pattern search: captain exception N4

**The captain granted N4 for exact and fuzzy MalQuery search only.**
The authorization is a new Invariant R exception for `PostMalQueryExactSearchV1` and `PostMalQueryFuzzySearchV1`, with `MalQuery:write`, validated patterns, and bounded results.
It admits neither `PostMalQueryHuntV1` nor multidownload scheduling nor either malware-download operation.
These ids remain absent even though a credential holding this scope could call them outside falcon-axi.

| Operation | Method and route | Effect | Required scope |
| --- | --- | --- | --- |
| `PostMalQueryExactSearchV1` | `POST /malquery/queries/exact-search/v1` | `malquery-search` | `MalQuery:write` |
| `PostMalQueryFuzzySearchV1` | `POST /malquery/combined/fuzzy-search/v1` | `malquery-search` | `MalQuery:write` |
| `GetMalQueryRequestV1` | `GET /malquery/entities/requests/v1` | `read` | `MalQuery:read` |

The [official MalQuery reference](https://developer.crowdstrike.com/api-reference/collections/malquery/) states WRITE for both searches and READ for request status.
falcon-mcp has no tool for these operations; [falconpy's generated table](https://github.com/CrowdStrike/falconpy/blob/06a5df8/src/falconpy/_endpoint/_malquery.py) maps their exact ids, methods and routes, while [PSFalcon](https://github.com/CrowdStrike/psfalcon/blob/b5f3774/public/malquery.ps1) wraps search as `Invoke-FalconMalQuery` (including `-Fuzzy`) and status as `Get-FalconMalQuery`.
PSFalcon corroborates pattern types `ascii` and `hex`, request-id UUIDs, and `meta.reqid`, `reqtype`, `status`.
Official success examples supply the metadata rows and `options.limit` request field.
These sources were checked on 2026-10-23; licensed-tenant behavior is unverified.

What N4 admits:

- `malquery search --string <ASCII> | --hex <bytes> [--fuzzy] [--limit N]`, defaulting to exact search.
  Both flags may be combined, with one pattern of each type.
  ASCII accepts 1-4096 printable characters with nonblank content; hex accepts 1-4096 literal byte pairs with optional spaces, normalized to lowercase without spaces.
  Wildcards, YARA, raw JSON, stdin bodies, and arbitrary options are absent.
- An integer result limit, default 20 and maximum 100, sent as `options.limit`.
  This is a conservative CLI cap, not a published API maximum.
  Fuzzy search renders synchronous metadata rows; exact search renders its UUID and status, with a status suggestion.
- `malquery status <id> [--limit N]`, one passive read of a UUID, with default 20 and maximum 100 displayed rows.
  Status has no upstream limit or pagination parameter and does not start or resume a job.
  Rows project only `sha256,family,filetype,filesize`.
  Results set `partial: true` and suggest narrower patterns when returned rows exceed the display limit, a supplied total exceeds the displayed count, or rows reach the limit without a known total.
  Upstream pagination totals are retained when supplied; missing totals stay unknown, and empty rows explain running requests, missing matches, or absent licensing without inventing completion.
- READ_ONLY blocks both searches before authentication but permits status and metadata.
  Neither search POST is automatically replayed; exact-search state may exist after an ambiguous failure.
  There is no automatic polling, cancellation operation, output file, or download.
- A search 403 is `SCOPE_DENIED`, explicitly naming `MalQuery:write`, N4, and not-licensed or not-permitted access.
  A search/status 400 is `UPSTREAM_ERROR`, without FQL advice.
  Malformed, mismatched-id, or error-bearing success responses fail rather than claiming no data.

The state and cost are corpus searches and an asynchronous exact-search request, without host execution or changes to detections, policies, or configuration.
Hunt consumes the metered hunt allowance and remains excluded; downloads deliver live malware and remain excluded despite READ scopes.
N4 is held by the exact id/method/route/scope seal and repeated body validation at the sink (§3.3 property 10), rather than relying on command discipline.
No live Falcon request is authorized or required; synthetic offline fixtures and transport fakes provide the validation evidence (§15).
The deliberate output changes are command discovery and scopes, top-level help, and auth status naming N4's optional write scope, with new search/status recorded invocations.

## 5. Credentials and secrets

### 5.1 The credential is an OAuth2 client credential pair

Falcon authenticates with `POST /oauth2/token`, exchanging a client ID and client secret for a bearer token
with a **standard 30-minute lifespan** (the Developer Center OAuth2 collection documents the 30-minute figure
on `oauth2RevokeToken`, whose purpose is revoking a token "before the end of its standard 30-minute
lifespan").

This is a hard divergence from both siblings and it drives §5.4.

### 5.2 Accepted input channels, in precedence order

The [AXI credential standard](https://github.com/knowttl/artium-axi/blob/main/docs/credential-standard.md)
supersedes the original dotenv credential contract.
The config path is selected by `--config`, then `FALCON_AXI_CONFIG`, then §12.1's platform default.
Profile selection is `--profile`, `FALCON_AXI_PROFILE`, the complete environment profile, `defaultProfile`,
then the only configured profile.
No profiles produces `PROFILE_REQUIRED`, multiple unselected profiles produce `PROFILE_AMBIGUOUS`, and an
unknown selected name produces `PROFILE_NOT_FOUND`.
The environment profile requires `FALCON_AXI_CLIENT_ID` and `FALCON_AXI_CLIENT_SECRET` as an atomic pair.
A partial pair produces `CONFIG_INVALID` and never falls back to a configured identity.
Explicitly selected profiles ignore environment profile fields, except the variables their SecretRefs name.
Profile selection stops at the first match, so a complete environment profile does not load file profiles.
The legacy-location hard cut still applies when the new config is absent.

Profile `clientSecret` holds an env or absolute local file SecretRef, defaulting to
`{"env":"FALCON_AXI_CLIENT_SECRET"}` when omitted.
Env reference names are validated when the config loads, including references in unselected profiles.
File contents are UTF-8 with the leading BOM and trailing whitespace removed.
Inline secrets and stored references are rejected; this tool has no login or credential writer.
Missing referenced secrets produce `AUTH_REQUIRED`.
The config and secret file read checks are specified in §12.1.

The old `~/.config/falcon-axi/credentials` dotenv file is never read.
When the new config is absent and the old file exists, `CONFIG_MOVED` names both paths and the new format.
Vendor-native `FALCON_CLIENT_ID`, `FALCON_CLIENT_SECRET`, `FALCON_MEMBER_CID`, `FALCON_BASE_URL`, and
`FALCON_PROXY_URL` remain deprecated aliases for one minor release, with a stderr notice.
`FALCON_BASE_URL` aliases `FALCON_AXI_REGION`; the other replacements insert `_AXI` after `FALCON`.
The replacement wins when both are set.

`FALCON_AXI_READ_ONLY` accepts `1`/`true` or `0`/`false`, case-insensitively, and rejects other values with
`CONFIG_INVALID` before authentication.
When enabled, it refuses `search start`, `search stop`, `identity activity`, `host usb`, and `malquery search` before token minting.
It also refuses execution by `rtr run` regardless of profile opt-in and confirmation; passive RTR history reads and local previews remain allowed.
It permits the fixed read-only Identity Protection documents despite their write-labelled scope.
`config path` reports `FALCON_AXI_WRITE_LOG` or the default state-dir `writes.log` path.
N3's journal and local host-lock contract is owned by §4.5.
State defaults to an absolute `XDG_STATE_HOME/falcon-axi`, otherwise `~/.local/state/falcon-axi` on POSIX,
and `%LOCALAPPDATA%\falcon-axi` on Windows, which ignores XDG variables.

### 5.3 No secret is ever a command-line argument

Hard rule, enforced structurally rather than by review.
Before parsing arguments, the CLI checks every declared flag and rejects any name matching
`/(secret|password|token|key|passphrase)/`.
`tests/offline/test_cli.py::test_a_secret_shaped_flag_cannot_be_registered` asserts that the guard rejects secret-shaped names.
This mirrors `awx-axi` §5.3, and the reason is the same: `argv` is visible in `ps`, in shell history, and in
agent transcripts.

**The guard targets secrets, and the member CID is a documented deliberate exception to it.**
`--member-cid` (§6.5) passes a value through `argv` even though §5.5 redacts `member_cid` on output, and the
guard pattern does not match it.
That is a decision, not an oversight: a CID is an **identifier, not a credential**, it grants nothing on its
own, and selecting a tenant without naming it is impossible.
The hard rule that credential and secret values never travel through `argv` is untouched.
A future contributor should therefore neither conclude that the guard already covers the CID nor "fix" the guard
by adding it to the secret pattern, which would remove the only per-invocation way to select a child tenant.
Section 12.1 records the exposure this accepts and the lower-exposure channels.

There is deliberately **no** `falcon-axi auth login` command.
There is nothing for it to do: Falcon mints a 30-minute token, so there is no long-lived artifact worth
storing, and a login command would only create a place to put a secret on disk.

### 5.4 No token cache in v1

**Decision: falcon-axi does not persist the bearer token.**
Each authenticated invocation mints its own token and discards it.
Authentication-free invocations mint no token (§5.6).

The cost is one extra request per authenticated invocation, published in §13.

The reason is that a cached bearer token is a **new secret at rest** that falcon-axi would own, with a file
mode to get right, an expiry to honor, and a tenancy tag to key on, in exchange for saving one request on a
CLI that is not in a hot loop.
falcon-mcp caches because it is a long-lived server process holding a session; the token-refresh locking in
`FalconClient._ensure_token_fresh` exists to collapse concurrent refreshes across threads, a problem a
single-shot CLI does not have.

Section 17.4 records the session-hook decision.

### 5.5 Redaction

Redaction is applied on the way to stdout and to stderr debug logging.
The authoritative case-insensitive key set is `REDACTED_KEYS` in `falcon_axi/render.py`.
It includes falconpy's credential keys, AXI profile keys, refresh tokens, the NG-SIEM tenant fields, and firewall `customer_id` tenant identifiers.
Resolved client IDs, client secrets, and minted access tokens are registered for invocation-local exact-value
redaction in raw, JSON-escaped, and URL-encoded forms.
Upstream strings additionally undergo JWT, PEM private-key, SAS signature, and `AccountKey=` pattern redaction.
Recon, Shield, case, firewall rule, and Intelligence detail records are recursively redacted before preview truncation so truncation cannot remove a secret pattern's closing marker.
Composite detection ids are the exception: the CID embedded in that identifier is not stripped.

The original credential key set is taken from falconpy's own `sanitize_dictionary`, which redacts exactly
`["access_token", "client_id", "client_secret", "member_cid", "token"]`.
Note it includes `member_cid`: CrowdStrike treats the tenant identifier as sensitive, and so does falcon-axi.
`cid` and `#repo.cid` are falcon-axi's addition for search events, not part of falconpy's set.
Certificate exclusion `children_cids` are also redacted as sensitive tenant identifiers.
One type of value is printed as-is, because redacting it would make the command unusable.
Alerts v2 composite detection ids contain the own-tenant CID or, when `--member-cid` selects a child tenant,
that child's CID.
Live verification on 2026-09-28 observed the forms `<cid>:ind:<aid>:<uuid>` and `<cid>:automated-lead:…`, with no
tenant value from that run recorded here.
`detection list`, `detection show`, and the home view print those ids as-is, because the id is the input to
`detection show`, including for a child tenant.
A help line that repeats that same id, such as `detection show <id> --full`, prints it as-is for the same reason.
Standalone member-CID values in auth status, suggestions, URLs, and logs stay masked or unprinted; the
`--member-cid` flag itself is allowed, but its standalone value is not echoed in output.
Suggestions replace FQL filters containing a `cid` or `member_cid` field (including dotted CID fields) with a quoted `<original-filter>` placeholder and instruct callers to reuse their original filter when continuing.
Examples elsewhere in this document use synthetic truncated ids such as `ldt:abc…:1234`; those examples are not
a masking rule.
Composite ids are printed as-is rather than masking the CID and restoring it on input.

Consequences:

- `auth status` prints whether a credential resolved and from which channel, never the value.
  With no effective member CID, it reports the own-tenant CID as unavailable because v1 has no verified source
  for it.
  With an effective member CID, it reports only that a member CID is selected and may show the existing masked
  suffix (`…a3b4`), never the unmasked value.
  v1 has no flag that reveals a CID.
- No error message, help line, or suggestion may interpolate a credential value.
  The error renderer takes structured fields, never a pre-formatted string carrying request context.
- Debug logging on stderr passes through the same redaction, because an agent transcript captures stderr even
  though the agent does not read it as data.
- A rejected base URL is never rendered, even after redaction.
  An arbitrary query key can carry a secret value that key-based redaction would not recognize, so an
  origin-policy failure reports only the violated component and the trusted allowlist.
  It never echoes the URL, any component value, a client ID, client secret, bearer token, member CID, or URL
  userinfo.

### 5.6 Missing or invalid credentials

| Condition | Code | Exit | Behavior |
| --- | --- | --- | --- |
| No profile resolves, including for `auth status` | `PROFILE_REQUIRED` | 1 | Names environment variables and the config.json path; no token is minted |
| Exactly one environment credential variable is present | `CONFIG_INVALID` | 2 | Names the missing half and does not fall through to a file profile |
| A selected SecretRef resolves to no value | `AUTH_REQUIRED` | 1 | Names the unresolved clientSecret field |
| `scopes`, `profile list`, or `config path` | none | 0 | Runs locally without resolving secrets or minting a token |

The three 401/403 branches follow falcon-mcp's `auth_failure_message`, which distinguishes exactly these cases
and attaches the same hints.
The destination is validated under §6.3 before any credential value is sent.

### 5.7 Provisioning asks for read scopes, plus three closed write-labelled exceptions

The README's [API client permissions](../../README.md#api-client-permissions) owns operator provisioning
and the Discover and Falcon Intelligence licensing guidance.
`falcon-axi scopes` projects the command-to-scope matrix from the registries (§8.3).
The provisioning invariant is unchanged: no write-labelled scope is permitted beyond captain exceptions N1, N2, and N4 (§4.3, §4.4, §4.6).
N4 optionally permits `MalQuery:write` solely for bounded exact/fuzzy search; status and metadata use `MalQuery:read`, and Falcon MalQuery licensing is required.
For N3's approved operations only, provisioning additionally permits `Real time response:read` for session history/hydration and the four guarded lifecycle operations, and `Real time response audit:read` for `RTRAuditSessions` alone.
These are optional command-specific grants, not new baseline requirements for ordinary reads.
The read-labelled RTR scope admits sensor-mediated execution upstream; falcon-axi's profile opt-in, exact confirmation, command allowlist, and READ_ONLY override remain mandatory regardless of the credential's grants.
No RTR admin or `Real time response:write` scope is requested, and no other RTR operation is admitted.

Section 17.7 owns the member-CID source-parity decision and its scope-evidence limitation.

Three properties of this rule:

- **The scope list is generated from the operation registry** (§3.3), so it cannot drift from what falcon-axi
  actually calls, and it cannot list a write scope other than the three §3.3 property 2 admits, because no
  other registered operation can have one.
  Each row's `access` column is derived from the scope itself rather than asserted, so `write` appears
  exactly where a write scope is genuinely required.
  The per-document read scopes of the GraphQL documents (§4.4) are projected from the document registry the
  same way.
- **A credential carrying broader scopes still cannot mutate anything through falcon-axi beyond N1, N3, and N4.**
  falcon-axi cannot restrict what a credential is permitted to do in general; that is the operator's
  provisioning decision.
  What it guarantees is narrower and enforceable: the closed registry in §3.3 means falcon-axi issues only
  the registered operations (§2.1), and for the GraphQL one only its registered documents, regardless of what
  the credential could otherwise reach.
  Only N1's NG-SIEM jobs, N3's guarded live-host lifecycle, and N4's bounded MalQuery searches admit state changes.
  A permissive credential is a risk to the *tenant*, not a hole in falcon-axi.
  That holds for `Identity Protection GraphQL:write` in particular: holding it lets falcon-axi read, and
  falcon-axi has no code path that sends a mutation.
- **falcon-axi does not silently accept a broader credential as normal.**
  When it can tell, it says so.
  It cannot enumerate granted scopes (§8.2, decision §17.2), so the honest behavior is
  documentation plus a line in `auth status` naming the three write-labelled scope exceptions.
  Its recorded output is owned by `tests/golden/auth-status.txt`; the current command-to-scope matrix is
  projected by `falcon-axi scopes` (§8.3).
  It never fails on a broad credential, because refusing to run against a credential the operator chose would
  be a policy decision falcon-axi is not entitled to make, and because failing closed there would push
  operators toward disabling the check rather than narrowing the client.

## 6. Regions and Flight Control

### 6.1 The regions

| Short name | Base URL |
| --- | --- |
| `us-1` (default) | `https://api.crowdstrike.com` |
| `us-2` | `https://api.us-2.crowdstrike.com` |
| `eu-1` | `https://api.eu-1.crowdstrike.com` |
| `us-gov-1` | `https://api.laggar.gcw.crowdstrike.com` |

This table is identical in three independently read sources: CrowdStrike's own falcon-mcp credentials
documentation, the falconpy Environment Configuration wiki, and falconjs `src/FalconCloud.ts`.

falconpy's wiki additionally names `USGOV2` as a region autodiscovery does not cover, so the four rows above
are the set falcon-axi resolves by short name and **not** necessarily the complete set of Falcon clouds.
`--region` therefore also accepts a full base URL, subject to §6.3's trusted-origin policy.
Section 17.3 records the approved region-table extension, which is separate implementation work.

### 6.2 Region selection

Precedence: `--region`, then the selected profile's `region`, then `us-1`.
The environment profile takes `FALCON_AXI_REGION`, with `FALCON_BASE_URL` as its deprecated alias.
An explicitly selected file profile ignores these environment fields.
`--region` and profile `region` accept a short name or URL, subject to §6.3.

### 6.3 Security property: credentials go only to a trusted origin

The resolved base URL is validated before token minting and again before every registered operation.
It must use HTTPS, carry no userinfo, query, or fragment, use the default HTTPS port, and have no path other
than `/`.
Any other scheme, an explicit non-default port, userinfo such as `user:pass@`, a non-root path, a query, or a
fragment is refused before a credential or token is sent.
Both network paths use manual redirect handling and refuse redirects before replaying a credential or bearer
token to another origin.

By default, the host must be one of the four documented hosts in §6.1 or a subdomain of the CrowdStrike-owned
parent domains `crowdstrike.com` or `gcw.crowdstrike.com`, matched on DNS label boundaries.
A host merely ending in the same text, such as `crowdstrike.com.example`, does not match.
`--region`, the environment profile's base URL, and a file profile's `region` continue to work when their
resolved origin passes this policy.
An origin refusal uses `ORIGIN_NOT_ALLOWED` and reports only `invalid_component` as `scheme`, `userinfo`,
`port`, `path`, `query`, `fragment`, or `host`, plus the allowed hosts and parent domains.
A token redirect with no region header, one naming the current host, or one after a re-mint uses
`ORIGIN_NOT_ALLOWED` with `invalid_component: redirect`.
On the first token request, a redirect naming an unknown region instead uses `REGION_MISMATCH` (§6.4).
Neither error renders the rejected URL or a component value.
This stronger rule is necessary because a secret can be smuggled under an arbitrary query key that §5.5's
key-based redaction cannot recognize.

An unknown Falcon cloud has exactly one opt-in: `--allow-unknown-origin`, passed in the same invocation.
The flag relaxes only the host allowlist; HTTPS, default-port, no-userinfo, root-path, no-query, no-fragment,
and redaction rules still apply.
An environment variable or profile field alone can never authorize an unknown origin.
Environment and profile are channels a typo or an injected instruction can poison silently, so sending a
client secret to a new origin must be a deliberate act in the invocation itself.

`--allow-unknown-origin` is an always-allowed global flag and is re-emitted in actionable suggestions
only for an invocation that explicitly supplied it.
This includes home-view continuations, cross-command pivots, and error remedies; it never becomes an ambient default.
There is no environment-variable or profile equivalent and no second bypass.

### 6.4 Autodiscovery is real, and falcon-axi uses it

**Verified mechanism**: the token response carries an `X-Cs-Region` header naming the cloud that actually owns
the credential.
falconpy's `autodiscover_region` reads `auth_result["headers"]["X-Cs-Region"]`, compares it to the requested
region, and swaps the base URL when they differ.
falconpy's wiki states autodiscovery covers `US1`, `US2`, and `EU1`, and that `USGOV1` and `USGOV2` users must
still supply the base URL.
The header is real beyond the SDK: `X-Cs-Region` appears in the documented standard response header set on the
Developer Center's Responses page.

**falcon-axi's behavior**: authenticate against the resolved region; read `X-Cs-Region` from the token
response; if it names a different known region, re-target the API base URL to that region and re-authenticate
once, then emit a one-line note on the home view and on `auth status`.
It never retargets more than once, and never retargets to a region it does not know.
A credential for a non-default cloud (such as us-2) is announced by a 308 from the default token endpoint, with
`X-Cs-Region` and an empty body, not by a 201.
That redirect is never followed, and its `Location` is never read: falcon-axi re-mints once against the
verified host for the named region.
A missing region header, or a second redirect, is `ORIGIN_NOT_ALLOWED`.
An explicit `--region` or a selected profile that already names the credential's cloud is unchanged.

If the region is wrong and autodiscovery cannot fix it (for example, an unknown region name), the failure is
`REGION_MISMATCH`, exit 1, and reports the observed `X-Cs-Region` value exactly as Falcon returned it.
When that value maps to a verified §6.1 short name, the remedy names that `--region` value.
When it does not, the remedy never fabricates a short name and instead tells the operator to supply a verified
full Falcon base URL with `--region <url> --allow-unknown-origin`, under §6.3's explicit opt-in policy.

Note for §16: **falconjs does not implement autodiscovery.**
`FalconClient` requires `cloud` up front and `OAuth2.refreshTokenInternal` builds its base path from it
(`src/middleware/oauth2.ts`, `src/FalconCloud.ts`).
Adopting the SDK would not buy this behavior.

### 6.5 Flight Control tenancy

Falcon's MSSP model is parent-child: a parent CID's API client can act on a child CID.

**The load-bearing fact: the member CID is selected at token mint, not per request.**
The Developer Center's `oauth2AccessToken` documents that "CID scoping can also be provided here", falconpy's
`OAuth2.token` takes `member_cid`, falconjs passes `memberCid` as the third argument to `oauth2AccessToken`,
and falcon-mcp passes `member_cid` into `APIHarnessV2` at construction.
falcon-mcp's PR describing the feature states that the parameter "is passed to the OAuth2 token endpoint during
authentication.
This scopes all subsequent API calls to the specified child CID."

Consequences for the CLI:

- **Tenant selection is per invocation, never per command within an invocation.**
  There is no `--member-cid` on a subcommand that could differ from the token's scope.
  It is a global flag (always allowed on every command, per AXI §6), alongside `--no-member-cid`, `--region`,
  and `--profile`.
- **A cross-tenant query is not possible in one call.**
  An agent comparing two child CIDs runs two invocations.
  This is a real limit and it is published rather than papered over.
  One partial exception is worth knowing: Spotlight's `cid` filter documents that a parent-CID caller with no
  `cid` filter receives "data about the parent CID and all its child CIDs", so `vuln list` from a parent is
  already fleet-wide.
- Precedence: `--no-member-cid`, then `--member-cid`, then the selected profile's
  `memberCid`, then none (act as the credential's own CID).
  The environment profile takes `FALCON_AXI_MEMBER_CID`; file profiles ignore that environment field.
  `--no-member-cid` explicitly clears any inherited environment or profile value for that invocation.
  Passing both member-CID flags is a `VALIDATION_ERROR` before token minting.
  `--member-cid` is a deliberate, documented exception to §5.3's `argv` guard, which targets secrets; §12.1
  states the exposure it accepts and when to prefer the profile or environment channel instead.

Section 17.6 owns the decision to omit child discovery.
Any future admission must satisfy the endpoint-specific corroboration rule in §2.2.
An operator discovers child CIDs in the Falcon console, then selects one with `--member-cid` or the documented
configuration channels.
Every Flight Control **write** (CID-group membership, user-group membership, MSSP role assignment) is
`Scope Flight Control: WRITE` and is excluded by §1.5.

### 6.6 Mismatch behavior

| Situation | Result |
| --- | --- |
| Member CID is not a child of the credential's parent | Token request returns 403; `TENANT_DENIED`, exit 1, with falcon-mcp's hint: verify this is a valid child CID "not the parent CID itself" |
| Member CID given but the tenant has no Flight Control | Same 403 path; help says to verify Flight Control access in the Falcon console or retry with `--no-member-cid` |
| An inherited member CID is invalid or no longer wanted | Re-run with `--no-member-cid` to authenticate as the credential's own CID without editing environment or profile configuration |
| Region is wrong but discoverable | Single silent re-target plus a note (§6.4) |
| Region is wrong and not discoverable | `REGION_MISMATCH`, exit 1, with the observed region and either its verified short name or the verified-full-URL path in §6.4 |

## 7. Pagination and rate limits

### 7.1 Falcon has three pagination models, not one

Verified from the Developer Center's Responses page, which documents all three, and corroborated by
falcon-mcp's `_extract_pagination`, which normalises across them.

1. **Offset pagination.**
   `body.meta.pagination` carries `{offset, limit, total}`, and the caller advances `offset`.
   This is the Alerts, Hosts, Discover accounts, Intel actor/report/malware, and Falcon Intelligence CVE model, documented on their collection pages.
   Discover logins use it too (§1.7).
   Recon lists use the offset contract in §2.4.
   Shield posture checks use an offset without this response metadata; §10.6 owns their pagination contract.
   Data Protection configuration also uses offset pagination (§10.7).
2. **Token ("deep") pagination.**
   `body.meta.pagination.after` carries an opaque token, passed back as `after`.
   The Developer Center states this is for "scenarios where the amount of data requested exceeds limits set by
   the API" and that for a couple of operations the token arrives in `offset` instead.
   This is the Spotlight model: `combinedQueryVulnerabilities` documents `after` as "a pagination token used
   with the `limit` parameter", and `PostCombinedAlertsV1` is documented as "intended for retrieval of large
   amounts of Alerts(>10k) using a pagination based on a `after` token".
   Discover assets and applications also use this model (§1.7).
   Discover IoT uses this token model as specified in §2.3.
3. **Timestamp marker pagination.**
   The position is a `_marker` timestamp embedded in the `filter` string, sorted `_marker.asc`.
   `indicator list` implements this model with fixed `_marker.asc` ordering.
   Its cursor stores the full last resource `_marker`, including the unique suffix, and resumes using
   `_marker:>'<marker>'` conjoined with the original filter in parentheses so OR filters retain their meaning.
   The strict comparison excludes the already returned resource without rounding away its suffix.
   A page that needs continuation but lacks an advancing marker fails with `UPSTREAM_ERROR`.
   The API total describes the remaining filtered dataset on that invocation, not an initial snapshot total.
   The model follows the official [pagination guide](https://developer.crowdstrike.com/sdks/python/responses/).
   The guide's inclusive comparison is tightened to strict comparison to avoid repeating the last resource.

Some reads have no pagination model.
Host network-address history returns the retained history without pagination (§1.7).
Sensor usage reports follow the unpaginated contract in §2.4.
Identity policy rules follow the unpaginated query contract in §2.3.
Host login history is a bounded window: `host logins` has no `--cursor`, and a host returning its limit
produces the saturation warning in §10.2 rather than a completeness claim.
An NG-SIEM query job also carries no `meta.pagination`, because it is a job rather than a collection query.
So `search status` has neither `--limit` nor `--cursor`, and the result set is bounded in the CQL itself with
`| head(N)` or an aggregate (§4.3).
That is stated here so a future reader does not add a fourth cursor model to §7.2's vocabulary on the
assumption that every falcon-axi list command must have one.

A fifth case is GraphQL's Relay model: the Identity Protection connection returns `pageInfo.hasNextPage` and an
`endCursor`, passed back as the `after` variable, with a `first` page size (§4.4).
It is carried by the same opaque `--cursor` as the `after` model, and like it has no offset and no total.

falcon-mcp adds a fourth complication falcon-axi must expect: the cursor is not always in the same place.
`_extract_pagination`'s docstring records that it lives in "nested `meta.pagination.next` (Shield), nested
`meta.pagination.after` (IOC/Spotlight), or top-level `meta.next` (CSPM assets/IOM)".
v1's Spotlight-backed `vuln list` is in that list, so the normalisation seam reads
`meta.pagination.after` from day one; cloud assets now also read top-level `meta.next` (§1.2.1).
Other locations remain part of the extension seam.
The implemented Shield response contract is specified in §10.6.
Firewall pagination also accepts `meta.pagination.next` under §10.8; top-level `meta.next` remains deferred for firewall lists.

**The 10,000-record wall is endpoint-specific.**
For Hosts, a captured `QueryDevicesByFilter` 400 response in falconpy discussion #985 says
`limit + offset must be less than 10000` and identifies `device-api` in `meta.powered_by`.
falcon-axi preflights that documented-by-observation condition and stops before issuing a Hosts request that
would violate it.

For Alerts, the official `GetQueriesAlertsV2` documentation defines a maximum `limit` of 10000 and an `offset`
but does not establish a `limit + offset` wall.
`PostCombinedAlertsV1` is separately documented as the `after`-token route for retrieving more than 10k
Alerts, but it is not a registered v1 operation.
falcon-axi therefore applies a defensive 10,000-result stop to an Alerts `--all` offset walk and stops before
it would continue past that boundary.
That stop is an explicit conservative policy, not a claim about undocumented `GetQueriesAlertsV2` behavior;
§17.12 records the decision to retain it.
Silently returning a short page would be the worst outcome, because the agent would believe it had seen
everything.

**A walk stops exactly at its governing wall, not a page short of it.**
Each requested page limit is `min(documented endpoint maximum, remaining row budget, wall headroom)`, so the
last page lands on the wall instead of overshooting it and being refused.
The two walls are not equally evidenced and the design does not blur them:

- For **Hosts** the governing wall is the **cited** one, the captured `QueryDevicesByFilter` 400 body reading
  `limit + offset must be less than 10000`, so the headroom is `9999 - offset`.
- For **Alerts** the governing wall is v1's **defensively enforced and unverified** 10,000-result stop
  (§17.12), so the headroom is `10000 - offset`.
- **Spotlight** `vuln list` has no such wall: it paginates by `after` token, so only the endpoint maximum and
  the row budget bound its pages.

Without the headroom clause, `host list --all --max-rows 10000` would request page 2 as offset 5000 limit 5000,
the preflight would refuse it, and the walk would surrender at 5000 rows with 9999 reachable.
With it, page 2 requests limit 4999 and the walk ends honestly at 9999.

**Hitting a wall mid-walk is a partial result, not a discarded read.**
Both walls mean "this walk cannot go further", which is the same thing `--max-rows` means, so both are reported
as a §7.2 partial result: every row already fetched is retained, the command exits 0 and prints `partial: true`,
a `stop_reason`, and a help item naming the remedy for that specific stop.
Returning an error envelope carrying none of the rows already fetched would be strictly worse than returning
them marked incomplete.
`PAGINATION_LIMIT`, exit 1, is therefore reserved for the case where a wall is reached with **no** rows
retained, which is the only case with nothing to return.

### 7.2 What the CLI exposes

One vocabulary across all three models.
The agent never sees an offset, an `after` token, or a `_marker`.

```
--limit N          rows to return in this single, non-walking call
--cursor <token>   opaque continuation token from a previous call
--all              walk pages until complete or the --max-rows cap
--max-rows N       maximum rows for --all (default 1000; requires --all)
```

Detection, host, account, and vuln lists implement this pagination vocabulary.
Cloud lists expose `--filter`, `--sort`, `--limit`, and `--cursor` only (§1.2.1).
Configuration and case lists use the one-page contract in §10.8.
Actor and report lists support one page per invocation with `--limit` and `--cursor` only (§2.3).
`cve list` also supports one page per invocation; §10 owns its query and continuation contract.
Discover asset, application, and login lists use the one-page contracts in §1.7.
`indicator list` exposes `--filter`, `--limit`, and `--cursor` only, with fixed ordering as defined in §7.1.
Its limit contract is in §7.3 and its output schema is in §10.2.
Custom IOC and host-group reads use the pagination contracts in §1.4.1.
Policy commands support one page per invocation with `--limit` and `--cursor` only (§1.2).
Section 2.4 owns Recon's single-page continuation and pagination-wall contract.
Exclusion and quarantine lists support one page per invocation under §1.2.2's contract.
`--max-rows` is intended only for list commands.
Identity directory, timeline, and sensor list commands support one page per invocation with `--limit` and `--cursor` only
(§4.4).
Shield posture checks also support only `--limit` and `--cursor`, with dedicated filters rather than FQL (§10.6).
Container, image, and serverless commands also expose one page per invocation, without `--all` or `--max-rows`; §2.5 owns their paging contracts.

**During an `--all` walk the walker owns page size, not `--limit`.**
`--limit` means rows returned by one non-walking call, which is the only call whose page size and result size
are the same thing.
A walk instead requests each page at `min(documented endpoint maximum, remaining row budget, wall headroom)`
per §7.1, and where the hydrate step's per-request cap is smaller than the query step's cap the walk also honors
the smaller one by chunking (§2.3): 10000 per Alerts query page hydrated in chunks of at most 1000, 5000 per
Hosts page, 100 per Discover accounts page, and 5000 per Spotlight page.
Paging a walk at `--limit`'s 20-row default would issue roughly fifty times the necessary requests on exactly
the path §7.4 warns will hit rate limits, and the row count an agent receives would be identical either way.
Section 13 publishes the resulting request counts.
The budget counts query rows, including ids that disappear before hydration, so concurrent deletions cannot
make a walk exceed its query budget.
The rendered count always reports only the retained rows.

`--cursor`'s value is a falcon-axi token: a base64 encoding of
`{operation, model, position, fingerprint}`.
`fingerprint` is an `HMAC-SHA-256` keyed by the client secret over canonical JSON containing the cursor's
operation, model, and position, the client ID, the effective query after shorthand flags are composed, the
effective sort, the resolved region origin, and the effective member-CID context.
The cursor contains only the operation, model, position, and non-reversible HMAC, never a credential value or
the sensitive CID.
Object keys are sorted and absent values are normalized before signing, so every caller uses one canonical
representation.

The shared cursor decoder recomputes that fingerprint from the current invocation and rejects any cursor-field,
query, sort, region, member-CID, or credential mismatch with `VALIDATION_ERROR`, exit 2, before making a
request.
It is opaque on purpose, so switching a domain from offset to token pagination is not a breaking change to the
CLI's contract, a cursor cannot silently continue a different dataset, and tampering with its position cannot
silently skip rows.
Secret rotation or switching credentials invalidates an existing cursor conservatively.

Every generated next-page suggestion carries forward all non-sensitive context required by the current
invocation alongside `--cursor`, including query- and sort-shaping flags, `--region`, `--profile`, an
explicitly supplied `--allow-unknown-origin`, and `--no-member-cid`, because the digest can validate context
but cannot restore it.
Query-shaping flags belong to the continuation builder; global context and the child-tenant reminder belong
only to the CLI help boundary, which covers every successful authenticated command's suggestions,
including home discovery, empty lists, detail pivots, and search lifecycle suggestions.
The boundary appends explicitly supplied `--region`, `--allow-unknown-origin`, and `--no-member-cid` flags
exactly once, including explicit `--config` and `--profile` selections.
Every replayed flag value and positional argument is POSIX shell-quoted so parsing and expansion preserve its
original value, including apostrophes, wildcard patterns, dollar signs, and embedded quotes.
The same quoting applies to detection and host empty-state suggestions that replay a query.
Each command suggestion help item encloses one complete command in outer backticks.
Literal backticks inside quoted arguments are part of the command, so global context is inserted before
its final outer delimiter, not before an argument's backtick.
A generated suggestion never contains a bare `--cursor` command.
Filter disclosure follows §5.5's redaction contract.
It never prints `--member-cid` with its standalone value, a URL component, or any other secret.
An Alerts v2 composite detection id may contain a selected child CID: where a help line repeats one as the
argument to `detection show`, it is printed as-is (§5.5).
When a successful authenticated invocation selects a child tenant and emits command suggestions, a separate
help item tells the operator to supply the same tenant selection, by name and never by value.
The cursor already binds a non-reversible digest of that context, so correctness does not depend on printing
it.

Every list prints the total when the API supplies one:

```
count: 20 of 384 total
```

When the API does not supply a total, the CLI reports an unknown total or only the number of rows shown.
Cloud lists use the latter form, `count: N`.
falcon-mcp made the same call: "`total` may be absent (some endpoints omit it) - report None rather than
inventing a count, so a caller can tell 'unknown' from a real total."

```
$ falcon-axi vuln list --filter "status:'open'"
count: 20 of unknown total
help[1]: "Run `falcon-axi vuln list --filter 'status:'\"'\"'open'\"'\"'' --cursor <token>` for the next page"
```

A walk that stops while more rows remain is a successful but explicitly incomplete read.
There are exactly two reasons a walk stops early, `--max-rows` and a §7.1 pagination wall, and both exit 0 and
print `partial: true`.
The walker reduces the final page's requested limit as §7.1 describes, so the stop lands on an API page boundary
and, where a continuation exists, it resumes without skipping or duplicating rows.
When the query step supplied a total, `count:` says `N of M total`; otherwise it says `N of unknown total`.
A capped result never silently resembles a complete result.

**A cursor exists if and only if the next position is reachable.**
That is the single rule for `continuation_cursor` everywhere it appears, and reachability is the only predicate:
more rows must remain **and** the next offset must be under the §7.1 wall governing that endpoint.
A guaranteed-dead cursor that costs an agent a turn to discover is worse than no cursor, and the decoder above
rejects a cursor whose effective query changed, so narrowing the filter cannot rescue one either.
Following an unreachable position would re-hit the wall with no rows retained, which §9.2 maps to
`PAGINATION_LIMIT` at exit 1.

The partial marker separately states **why** the walk stopped, in a `stop_reason` field, because §9.3's
obligation to say what to do next applies to a partial success exactly as it does to a failure.
`stop_reason` never decides whether a cursor exists; the reachability rule above does.
When the row budget is spent at the same row the wall is reached, `stop_reason` is `max_rows`, because the budget
is the constraint the operator set and can change.

The two jobs combine into three cases, all derived from the rule rather than restating it:

| `stop_reason` | Next position | Cursor | The matching help line |
| --- | --- | --- | --- |
| `max_rows` | reachable | yes | Raise `--max-rows`, or follow `continuation_cursor` to resume from this position |
| `max_rows` | at the governing wall | no | Say the budget was spent **and** that the remaining rows are unreachable through falcon-axi: narrow the filter so the result set fits under the wall, and for Alerts name `PostCombinedAlertsV1` with `after` pagination as the documented route v1 does not register |
| `pagination_limit` | at the governing wall | no | The same wall remedy, narrowing the filter and naming the documented route where one applies |

The middle case is not an oversight and must not read as one: raising `--max-rows` alone would not reach further,
so its help line carries the wall remedy as well as the budget fact.

Configuration and case list limits and their sources are specified in §10.8.

A `--limit` above the ceiling is a `VALIDATION_ERROR` naming the ceiling, not a silently capped request:
falcon-axi never lets an agent believe it asked for 5000 rows and received a capped page.
Above 1000 rows, `detection list` chunks the hydrate step (§2.3) and says nothing about it, because the chunk
count is an implementation detail while the row count is not.

Two domain-specific input rules, both from the collection pages:

- **`vuln list` requires a filter.**
  `combinedQueryVulnerabilities` documents "You must provide a filter".
  So `vuln list` with no `--filter` and no filter-shorthand flag is a `VALIDATION_ERROR`, exit 2, suggesting
  `--host <device_id>` or `--severity`, rather than a 400 from the API.
- **Spotlight filters do not support wildcards.**
  The same page says "Wildcards `*` are unsupported".
  `vuln list --filter` containing `*` is rejected locally regardless of whether the character appears inside or
  outside an FQL-quoted value, so `cve.id:'CVE-*'` is rejected too.
  `host list` accepts wildcards because the Hosts filter table documents `hostname` as supporting them.

### 7.4 Rate limits

**What is documented.**
Every JSON response carries `X-Ratelimit-Limit` and `X-Ratelimit-Remaining` headers; both appear in the
Developer Center's canonical response structure, whose `headers` branch is described as carrying "the overall
remaining requests available within your current rate limit".
A 429 means "Rate limit exceeded.
Too many requests in a short period." (falcon-mcp's `ERROR_CODE_DESCRIPTIONS`).

**What is documented only in an SDK, and is labelled as such.**
CrowdStrike's Go SDK handles an **`X-RateLimit-RetryAfter`** header on 429 whose value is an **epoch-seconds
timestamp**, falling back to exponential backoff when the header is absent, invalid, or in the past, and
explicitly *not* honoring it on 5xx.
That is read from gofalcon commit `208826a`'s tests, not from an API reference page.
falcon-axi implements the same rule and treats a missing header as the normal case rather than an error.

**What is not published.**
Numeric per-endpoint limits.
falcon-axi therefore never hard-codes a rate and never pre-throttles.

**Policy.**

- On 429: sleep until `X-RateLimit-RetryAfter` if it parses to a future time, else exponential backoff from
  500ms, jittered, up to 3 attempts.
- On 500, 502, 503, 504: exponential backoff only, up to 3 attempts, ignoring any retry-after header.
- N3's execution-tier operations and N4's search POSTs do not inherit this generic retry policy; their replay contracts are owned by §4.5 and §4.6 respectively.
- After the last attempt: 429 maps to `RATE_LIMITED`, 500 maps to `UPSTREAM_ERROR`, and 502, 503, or 504
  maps to `UPSTREAM_UNAVAILABLE`, all with exit 1 and any observed wait reported.
- `X-Ratelimit-Remaining` is surfaced on `auth status` and, when it drops below 10% of `X-Ratelimit-Limit`, as
  a note on list output, so an agent about to start a `--all` walk can see it coming.

## 8. API scopes

### 8.1 Scopes are declared per command, in code

Each command's registry entry declares the operations it calls, and each operation declares its scopes (§3.3).
For GraphQL identity commands, the document registry also declares the domain read scopes (§4.4).
A command's required scope set is their union, except that policy and exclusion commands require only the operations
selected by `--type` (§1.2 and §1.2.2).
The matrix marks policy and exclusion scope alternatives as `selected --type` rather than requiring every type's scope.
This is falcon-mcp's `API_SCOPE_REQUIREMENTS` idea with the key changed from operation to command, because the
operation name is an implementation detail an operator never sees while the command name is what they ran.

The complete matrix is projected by `falcon_axi/scopes.py`, with its recorded output contract described in §8.3.
The local required-check set asserts that write-labelled scopes occur only on commands N1, N2, and N4 admit.

### 8.2 A missing scope is an actionable failure

Falcon answers a scope failure with **403**.
falcon-mcp's response is the model to copy: on a 403 it looks up the operation's required scopes and returns
them with a resolution string naming the Falcon console.

falcon-axi's version, on stdout in TOON per AXI §6:

```
error: this API client is not permitted to read detections
code: SCOPE_DENIED
required_scopes[1]: "Alerts:read"
help[2]: "Grant `Alerts:read` (read only) to the API client in the Falcon console under Support and resources > API clients and keys","Run `falcon-axi scopes` for the full scope matrix"
```

Two honesty notes carried in the help text rather than assumed away:

- A 403 can also mean the API client is disabled, or that the member CID is not a child of this parent (§6.6).
  falcon-axi distinguishes the tenancy case because it happens at token mint, before any operation; a 403 on
  an operation after a successful token mint is reported as a scope problem with "or the API client is
  disabled" in the help.
- falcon-axi cannot enumerate granted scopes ahead of time.
  Section 17.2 records the decision and its evidence.
  `auth status` therefore makes no claim about observed or granted scopes.

### 8.3 Scopes are documented for the operator

`falcon-axi scopes` prints the whole matrix from the operation and document registries (§8.1), so the person
provisioning the API client can grant exactly what is needed and nothing more.
Its recorded output contract combines the `tests/golden/scopes.txt` template with committed per-command references under the reconstruction contract in [v1-python.md §5](v1-python.md#5-behavior-that-must-not-change-during-the-port).
Documentation must not hand-copy that matrix.
The `access` column is derived from the scope string rather than asserted, so the offline scope checks can
hold it to the registries.
User-facing provisioning guidance is owned by the README's API client permissions section.
The output preserves §17.7's scope-evidence limitation for member-CID token minting.
Because `scopes` is a local registry projection, a new operator can run it before credentials exist and it
never mints a token.

## 9. Structured errors

### 9.1 One envelope

Errors go to **stdout**, in TOON, per AXI §6.

```
error: "<what went wrong, in plain language>"
code: <STABLE_CODE>
help[N]: "<actionable next command>","<another>"
```

Exit codes: `0` success including empty results, `1` error, `2` usage error.
AXI §6's idempotent-mutation no-op rule has no v1 instances, because there are no mutations.

### 9.2 The code table

| Code | Cause | Exit |
| --- | --- | --- |
| `VALIDATION_ERROR` | Unknown flag or subcommand, missing required argument, blank `--filter`, invalid relative `--since` window, invalid identity account subject (§4.3), missing required `--filter` on `vuln list`, `--limit` above the API ceiling, unknown `--fields` name, cursor context mismatch, conflicting member-CID flags | 2 |
| `CONFIG_INVALID` | Invalid config/schema/SecretRef, partial environment profile, or invalid boolean | 2 |
| `CONFIG_INSECURE` | File provenance, POSIX permissions, or diagnostic Windows DACL check fails | 1 |
| `CONFIG_MOVED` | Only the legacy dotenv file exists | 1 |
| `PROFILE_REQUIRED` | No profile is available | 1 |
| `PROFILE_AMBIGUOUS` | Multiple profiles exist without a selection or default | 1 |
| `PROFILE_NOT_FOUND` | The selected profile does not exist | 1 |
| `FQL_INVALID` | 400 whose body indicates a filter syntax problem, or a locally detected wildcard in a Spotlight filter | 2 |
| `AUTH_REQUIRED` | The selected profile's SecretRef resolves to no value | 1 |
| `AUTH_FAILED` | 401 from the token endpoint, or 403 with no member CID configured | 1 |
| `SCOPE_DENIED` | 403 on an operation after a successful token mint; required scopes named, including the write-labelled scopes admitted by N1, N2, and N4 | 1 |
| `TENANT_DENIED` | 403 at token mint with a member CID configured | 1 |
| `ORIGIN_NOT_ALLOWED` | Base URL violates the scheme, authority, path, or trusted-host policy in §6.3 | 1 |
| `REGION_MISMATCH` | Wrong region and autodiscovery could not resolve it | 1 |
| `NOT_FOUND` | An ID lookup returned no resource or 404, or host login history returned 400 with "invalid device id" | 1 |
| `PAGINATION_LIMIT` | A §7.1 offset wall was reached with no rows retained: a first Hosts request would violate the cited `limit + offset` rule, or an Alerts walk hit the defensive 10,000-result stop before any row was fetched. A wall reached with rows already fetched is a cursorless `stop_reason: pagination_limit` partial result at exit 0 instead (§7.2) | 1 |
| `RATE_LIMITED` | 429 after retries exhausted | 1 |
| `UPSTREAM_ERROR` | 500, any unmapped 4xx, a GraphQL 400, or a GraphQL HTTP 200 with errors or without object-valued data (§4.4) | 1 |
| `UPSTREAM_UNAVAILABLE` | 502, 503, 504 after retries | 1 |
| `NETWORK_UNREACHABLE` | DNS failure, connection refused, connect timeout | 1 |
| `TLS_UNTRUSTED` | Certificate verification failed | 1 |
| `READ_ONLY_VIOLATION` | An unregistered operation was requested (§3.3), or FALCON_AXI_READ_ONLY blocked a search lifecycle command; nothing was sent | 1 |
| `UNKNOWN` | Anything unmapped | 1 |

`READ_ONLY_VIOLATION` is the runtime registry backstop and the explicit read-only switch's refusal.
Registry failures name the attempted operation ID; policy failures name `FALCON_AXI_READ_ONLY`.

### 9.3 How a failure tells an agent what to do next

Each code maps to a fixed remedy shape, so the agent's next move is deterministic:

| Code | The next move it hands the agent |
| --- | --- |
| `AUTH_REQUIRED` | The unresolved clientSecret field |
| `PROFILE_REQUIRED` | The two environment variable names and the config.json path |
| `CONFIG_INVALID` | The invalid field or missing environment variable, without any secret value |
| `CONFIG_INSECURE` | The path and its platform-specific permission repair |
| `CONFIG_MOVED` | Both paths and the replacement config format |
| `PROFILE_AMBIGUOUS` / `PROFILE_NOT_FOUND` | Select a configured profile with `--profile` |
| `SCOPE_DENIED` | The exact required scope strings to grant, plus `falcon-axi scopes`; N2 explains why GraphQL needs write-labelled access (§4.4) |
| `TENANT_DENIED` | Verify the child CID in the Falcon console, or retry with `--no-member-cid` |
| `ORIGIN_NOT_ALLOWED` | The trusted host allowlist, plus `--allow-unknown-origin` only for a deliberately selected unknown Falcon cloud |
| `REGION_MISMATCH` | The observed region exactly; use its verified short name when mapped, otherwise supply a verified full base URL with `--allow-unknown-origin` |
| `FQL_INVALID` | The FQL operator rule that was probably violated, plus `--help` for the field list |
| `PAGINATION_LIMIT` | Narrow the filter so the result set fits under the wall; the documented Alerts route beyond 10k, `PostCombinedAlertsV1` with `after` pagination, is not registered in v1. Never a cursor, because no continuation is reachable; the `pagination_limit` partial result carries this same cursorless remedy when rows were retained (§7.2) |
| `RATE_LIMITED` | Wait for the reported retry-after, narrow the FQL filter, or drop `--all` |
| `VALIDATION_ERROR` | The command's valid flags, inlined (AXI §6) |

The `FQL_INVALID` help text is worth its own note.
falcon-mcp's 400 description is a whole FQL lesson: "Invalid request.
Check your filter syntax - FQL uses + for AND, `,` for OR, and values must be quoted."
That is exactly the shape AXI §6 wants, because the mistake it names is the one an agent actually makes, and
falcon-axi's `FQL_INVALID` help carries the same rule plus a correct example for the specific domain.
For Discover inventory and host network history, the operation selects the filter example and identifier-list remedy, so errors point back to the relevant inventory rather than an unrelated domain.

### 9.4 Translation, never passthrough

Falcon's error detail is in the body, not only the status line.
The documented response envelope always carries an `errors` list, where "each error object will contain a
single `code` and `message` value".
falconjs's `FalconError.text()` reads `errors[0].message`.

falcon-axi extracts `errors[*].message`, maps status plus body shape to a code from §9.2, and composes its own
message.
Raw Falcon bodies never reach stdout, no HTTP status number is printed as an error, and no suggestion names a
Falcon endpoint or an SDK.

`meta.trace_id` is present on responses and is the identifier CrowdStrike support asks for.
falcon-axi prints it on `UPSTREAM_ERROR` and `UPSTREAM_UNAVAILABLE` only, as `trace_id:`, because on those
codes the operator's real next step is a support ticket.

A lesson borrowed from `azure-axi`'s AGENTS.md rather than relearned: a hand-authored error fixture proves only
that the code agrees with its author.
Synthetic fixtures can prove deterministic translation behavior but cannot independently prove that a real
Falcon response has the assumed shape.
Each error-translation pattern in §9.2 therefore remains provisional until a real, safely observed error body
confirms it without persisting the response.
Section 18 records endpoint-specific confirmations, including the Hosts pagination wall and the slice C
login-history and Discover scope errors.
Unobserved error shapes remain provisional.
Section 15 owns the validation policy; source parity cannot remove that provisional status.

### 9.5 Unknown flags fail loud

Per AXI §6, an unrecognised flag is rejected by name before any HTTP call, with the subcommand's valid flags
inlined so the correction takes one turn.
For example, `detection list --sev high` reports `VALIDATION_ERROR`, suggests `--severity`, and
lists the current flags from the command registry rather than silently accepting `--sev`.
Flag sets are per subcommand.
The always-allowed globals are `--help`, `--region`, `--allow-unknown-origin`, `--member-cid`,
`--no-member-cid`, `--config`, and `--profile`.

## 10. TOON output

`cve list` emits `cves[N]{cve,severity,cvss_v3_score,exploit_status}`, restoring query order after hydration.
Its count comes from the query total, and its offset advances by queried ids even when hydration returns fewer records.
Unknown totals stay unknown; a full page without a total offers a continuation.
`--severity` accepts low, medium, high, critical and composes `severity:'UPPERCASE'`.
`--since` composes `publish_date:>'now-<window>'`; `--filter` is optional FQL, grouped when combined with shorthands.
Empty initial queries report zero CVEs with filter context; empty continuations report no more CVEs.
The cursor binds the effective query, operation, credential, region, and tenant selection as in §7.2.

`vuln show` emits `vulnerability` with id, cve, severity, hostname, device_id, description, base_score,
exprt_rating, status, created, updated, product, platform, os, and local_ip.
It reads the existing Spotlight entity fields without expanding remediation or evaluation logic.
An empty or 404 entity response is `NOT_FOUND`; a nonempty response lacking the requested id is `UPSTREAM_ERROR`.
Both new reads are matched to the official API reference and SDKs, with synthetic offline tests rather than tenant validation.

### 10.1 The boundary

Internal logic is JSON; conversion to TOON happens once, at the output boundary, per AXI §1.
The Python implementation's stable TOON encoder quotes strings beginning with `#`.
Search `query` and `parsed_query` fields therefore quote hash-prefixed CQL, as pinned by the golden search documents.

Two implementation facts inherited from the fleet, both recorded in `azure-axi`'s AGENTS.md as sharp edges
found by real work rather than assumed from the TOON spec:

- `encode()` from `@toon-format/toon` inlines primitive arrays comma-separated, which breaks the `help[N]:`
  block shape and mangles any suggestion containing a comma.
  So the help block, the `count:` line, and truncated detail values are **hand-formatted**, exactly as `gh-axi`
  and `azure-axi` do; row data still goes through `encode()`.
  The hand formatter applies TOON §7 quoting and escaping to every help element before joining them with the
  active delimiter, including elements containing commas, colons, quotes, or command examples.
  Every tabular string cell and object-field string is also quoted when TOON §7 requires it, including values
  containing an active delimiter or a colon, so row disambiguation and object parsing cannot reinterpret data.
- `encode()` quotes an `error:` message containing `, ` or `: ` or starting with `-`.
  Error messages are therefore worded to avoid those sequences.

The TOON spec (v4.1 working draft) is the authority for the syntax itself: UTF-8 with LF, tabular headers of
the form `key[N]{fields}:`, and the quoting rules in its §7.

The shipped `--fields` flag extends the default row on detection, host, and vuln lists.

carry `source_endpoint_host_name`, `agent_id`, and `source_account_*` instead.

  Missing values in the added columns read `n/a`, including on endpoint rows in a mixed page.

filter on is exactly where an agent will look for a way to set it.

NG-SIEM search has no fixed row schema, because a CQL result set has no fixed shape:
the columns are whatever the query projected, and an aggregate returns different columns again.

rows matched, `events_scanned` is how a zero-row answer is told apart from a query that scanned nothing, and
`parsed_query` is the API's normalized filter from `metaData.filterQuery.queryString`.
It echoes the filter part only; stages after the first pipe are not echoed.
Keep the existing field name for callers and explain this boundary in completed-search output and `search status --help`, which also feeds the generated skill reference.

There is no `total`: the GraphQL connection is read for `nodes` and `pageInfo` only, and a total is never
invented (§7.2), so `count` says how many rows this page shows and a continuation cursor appears exactly when
`pageInfo.hasNextPage` is true.
`risk` is the severity with the numeric score in parentheses, and a timeline cell an event type does not carry
is `unknown` rather than a dropped column, because the rows of one table must share a shape.
Empty directory descriptions and timeline window messages pass through the TOON encoder, so caller text
containing newlines or quotes remains one string value.
`identity show` prints one `identity` object whose `risk_factors`, `accounts`, `associations`, and
`open_incidents` are lists, with the first 25 associations unless `--full` is given, because a local-admin
association list has no server-side bound and no pagination of its own.
Open incidents are bounded to the first 10 in the query.
When their `pageInfo.hasNextPage` is true, the detail adds `open_incidents_partial: true` and a help item
stating how many are shown and that more exist in Falcon; `--full` expands associations only.
Timeline file-operation events select `targetEntity`, `userDisplayName`, `endpointDisplayName`, and
`ipAddress`, but not the unsupported `sourceEntity` field.

### 10.3 Pre-computed aggregates

AXI §4's argument is that the expensive cost is the follow-up call.
One aggregate is both available and cheap enough to include:

- **The total**, from `meta.pagination.total`, free on the query step (§2.3).

`detection summary` computes a severity rollup on demand with one `PostAggregatesAlertsV2` request.
Section 2.2 owns its scope and response-shape evidence.
The command uses a fixed `terms` specification on `severity_name`, named `severity`, with `size: 100` and
`missing: unknown`, and includes hidden alerts by Falcon's default, matching `detection list`.
It accepts the same `--severity`, `--status`, `--product`, `--since`, and `--filter` composition as that list.
There is no list pagination, hydration, or client-side 10,000-result boundary on this aggregate.
Output is a `severities` table with `severity,count` columns in Falcon's bucket order.
If Falcon reports `sum_other_doc_count > 0`, `other_count` exposes the number of alerts in omitted buckets.
Empty resources or buckets with no omitted alerts state `0 detections` with the filter context; malformed or error-bearing responses fail
with `UPSTREAM_ERROR` instead of claiming zero.
No follow-up help is needed for this self-contained answer.
Status and tactic rollups remain optional future extensions.
The home view makes no aggregate request.
This contract is checked with synthetic fixtures and goldens, without tenant validation.

### 10.4 Truncation

Detection detail views carry long text (behavior descriptions, command lines, the full pattern context).
Per AXI §3, truncate and say how much is missing:

```
$ falcon-axi detection show ldt:abc…:1234
detection:
  id: "ldt:abc…:1234"
  severity: High (70)
  tactic: Defense Evasion
  technique: Masquerading
  hostname: WIN-DC-01
  device_id: abc123…
  status: new
  first_seen: "2026-07-28T10:58:02Z"
  cmdline: "powershell.exe -enc SQBFAFgAI… … (truncated, 2841 chars total)"
help[1]: "Run `falcon-axi detection show ldt:abc…:1234 --full` to see the complete command line"
```

Limit: 800 characters per field, inside AXI §3's 500-1500 band.
The `--full` hint appears only when something was actually truncated.
A field is never omitted entirely.

Command lines get one extra rule specific to this domain: a truncated command line is **still
attacker-controlled text**.
It is emitted quoted, and truncation happens on a character boundary with no attempt to pretty-print, so
nothing in the pipeline reinterprets it.

### 10.5 Definitive empty states

Per AXI §5, the zero is stated with the filter that produced it:

```
$ falcon-axi detection list --severity critical --since 24h
detections: 0 critical detections in the last 24h
help[1]: "Run `falcon-axi detection list --severity critical --since 7d` to widen the window"
```

For detection, host, account, and vuln lists, an empty initial page reports zero matches in the tenant or supplied filter.
An empty continuation after a nonzero offset or an `after` token instead reports `no more accounts`,
`no more detections`, `no more hosts`, `no more vulnerabilities`, `no more classifications`, or `no more policies`,
without a cursor or widening suggestions.
An exhausted page does not imply that the inventory or filtered result set is empty.
An absent total may require one final empty page to establish exhaustion.
Cloud lists report an empty page as `0 cloud_assets`, `0 ioms`, or `0 cloud_risks` with tenant or supplied-filter context, including on continuation.

### 10.6 Shield posture checks

`shield list [--status <status>] [--impact <impact>] [--limit N] [--cursor <token>]` and
`shield show <id> [--full]` both call `GetSecurityChecksV3` (§2.1); §2.2 owns its scope and read evidence.

List rows contain `id`, `name`, `status`, and `impact`.
Status and impact filters are case-insensitive locally and sent using the API's documented spelling.
The [generated command reference](../../skills/falcon-axi/references/shield-list.md) lists the accepted values from the command declaration.
No FQL filter is advertised because this operation uses dedicated query parameters.
Section 7.3 owns the default limit and local cap.
Pagination advances `offset` by the number of returned records and uses the existing signed cursor bound
to filters, operation, credential, region, and selected tenant.
The documented successful response is a top-level check array with no total; list prints `unknown` for the total.
Both commands reject non-array bodies and records without a nonempty string ID as `UPSTREAM_ERROR`, rather than claiming no checks matched.
A full page allows another read, which can return the explicit `no more Shield checks` state.
An initial empty page says `0 Shield checks matching this query`.
Section 13 owns the request cost.

Show sends the ID as the documented `id` query parameter and requires an exactly matching response ID.
An empty or 404 result is `NOT_FOUND`; a nonempty response with no matching ID is `UPSTREAM_ERROR`.
The detail preserves all returned fields through the existing redaction boundary, truncating long text at
800 characters with a `--full` suggestion only when text was shortened.
Section 1.3 owns the deferred Shield reads; Invariant R (§0) excludes every Shield write.

### 10.7 Data Protection reads

`classification list|show` and `data-policy list|show` read configuration under `Data Protection:read`.
The noun `data-policy` distinguishes these policies from endpoint policy families.
Lists query IDs then hydrate within §7.3's batch ceiling and restore query order, preserving the query total.
The maximum offset is 10000; §7.3 owns page defaults and query ceilings.
Both support raw `--filter`, `--sort field.asc|desc`, and context-bound `--cursor` continuation.
Policy lists require `--platform win|mac`, sent as `platform_name`; policy detail needs only `ids`.
Cursors bind the platform alongside the filter, sort, credential, region and tenant selection.
When more results exist beyond offset 10000, output carries `partial: true`, `stop_reason: pagination_limit`,
and a narrowing suggestion, without an unusable cursor.
Classification lists show `id`, `name`, `protection_mode`; policy lists show `id`, `name`, `is_enabled`, `precedence`.
Details retain the full read record, including classification rules or policy properties and references,
with the existing recursive secret and CID redaction at the output boundary.
There are no create, update, delete, precedence-change or response operations.

The official [Data Protection Configuration API](https://developer.crowdstrike.com/api-reference/collections/data-protection-configuration/)
and falconpy 1.6.5's `_endpoint/_data_protection_configuration.py` confirm the four GET operations and parameters.
[falcon-mcp `modules/data_security.py` at ece8575](https://github.com/CrowdStrike/falcon-mcp/blob/ece85750f8c9445850c61315f8cdbdf21dbf2b4f/falcon_mcp/modules/data_security.py)
corroborates query/hydrate, platform selection, and `classification_properties` / `policy_properties` field names.
Its `common/api_scopes.py` maps all four to `Data Protection:read`.
The [generated command reference](../commands.md#classification-list) owns command usage; [read-only enforcement and validation](../read-only.md#evidence-and-validation) records the evidence limits.

There is no standalone event read in the supported falconpy Data Protection collection, so no new event operation is registered.
Following that same falcon-mcp module, detections use `falcon-axi detection list --product data-protection`.
For classified-file events, use `falcon-axi search start --query '#event_simpleName=Event_DataProtectionClassifiedFileEvent | head(200)'`, then `falcon-axi search status <id>` and `falcon-axi search stop <id>` if the job is left running, retaining N1's job lifecycle boundary.
Other configuration entities, evidence downloads, and any write remain outside this slice.

### 10.8 Configuration and case reads

`firewall rule list|show`, `firewall group list`, `ioa group list`, `correlation-rule list`, and
`case list|show` are ordinary reads with no new write authority.
Lists accept `--filter`, `--limit` (default 20), and the existing context-bound `--cursor`.
Firewall lists use the server's `meta.pagination.next` or `after` token as the next `after` parameter,
matching falcon-mcp's firewall and base modules.
When neither token is present, they advance `offset` by the query resource count, using the response offset and total when supplied.
Their context-bound cursors carry either an offset or a token, with server tokens taking precedence.

Totals are captured from the query response before hydration and remain unknown when absent.
The firewall page ceiling is 5000; the other three lists use falcon-mcp's 500 ceiling.
Hydration reads at most 100 ids per request, restoring query order and retaining query totals.

### 11.1 The home view

Capped at 5 rows.

### 11.2 The help hierarchy

Three levels, each answering a different question, per AXI §10:

1. `falcon-axi` (no args): what is happening right now, plus a few next steps.
2. `falcon-axi --help`: the noun list, one line each, plus the global flags and the read-only boundary with the shipped captain exceptions.
   Once N3 ships, describe its guarded execution explicitly rather than claiming all commands are passive reads.
3. `falcon-axi <noun> <subcommand> --help`: that subcommand only.
   Flags with defaults, required arguments, and 2-3 worked examples including a realistic FQL filter.
   It never dumps the whole CLI.

The valid-noun list and every suggestion the CLI emits are derived from the command registry, so a suggestion
can never name a command that does not exist.
That derivation is what `azure-axi`'s AGENTS.md identifies as keeping a partially built CLI from advertising
commands it cannot run, and it matters twice here: v1 selects only a few upstream domains, and the commands it
does not have include every mutation in §1.5.

### 11.3 FQL is discoverable, because it has to be

FQL is where an agent with no prior knowledge fails.
Its rules are unusual and unguessable: `+` is AND, `,` is OR, the words AND and OR do not work, values are
single-quoted, and relative dates are lowercase (`now-7d`).
falcon-mcp treats this as important enough to ship a per-module FQL guide as an MCP resource plus a shared
`FQL_BASE_OPERATORS` block; 25 of its 154 registered names are FQL guides.

falcon-axi cannot ship MCP resources, so the equivalent lives in three places:

- `--help` on each list subcommand carries that domain's filterable fields and two working filter examples.
  The field lists are real: the Hosts collection page documents 22 filterable fields including `hostname`
  (wildcard-capable), `platform_name`, `last_seen`, and `status`; the Spotlight page documents `aid`,
  `cve.id`, `cve.exprt_rating`, `cve.exploit_status`, `status`, and `created_timestamp` among others.
- Common filters get first-class flags, so the usual case needs no FQL at all: `--severity`, `--status`,
  `--since`, `--hostname`, `--platform`, `--host`, and on `detection list` and `detection summary` `--product`.
  The accepted product values are owned by `PRODUCTS` in `falcon_axi/fql.py` and displayed by
  `falcon-axi detection list --help`; §18 records their source.
  These compose into one FQL string internally.
- `--filter` is the escape hatch for raw FQL, and `FQL_INVALID` (§9.3) teaches the operator rules on failure.
  In all three list domains, a raw filter composed with shorthands is parenthesized before AND-composition,
  so each shorthand constrains every OR branch.
  A raw filter supplied alone is sent unchanged.

For every command accepting these flags, a whitespace-only `--filter` or an invalid relative `--since`
window is a `VALIDATION_ERROR` during argument parsing, before credential resolution or OAuth token minting.
`--help` bypasses these value checks and remains authentication-free.
The no-request regression contract is pinned in `tests/offline/test_cli_input_validation.py`.

## 12. Session integration and configuration

### 12.1 Configuration holds no secrets

Configuration follows §5.2 and the AXI credential standard.
The default config directory is an absolute `XDG_CONFIG_HOME/falcon-axi`, otherwise `~/.config/falcon-axi`
on POSIX, and `%APPDATA%\falcon-axi` on Windows, which ignores XDG variables.
Paths resolve on every call using `Path.home()`, never a home path captured at import time.
No configuration is discovered from the working directory.

```json
{
  "version": 1,
  "defaultProfile": "prod-us",
  "profiles": {
    "prod-us": { "region": "us-1", "clientId": "<client-id>", "clientSecret": { "env": "FALCON_AXI_CLIENT_SECRET" } }
  }
}
```

A strict profile permits only `region`, `memberCid`, `clientId`, `clientSecret`, and N3's optional `rtr` object (§4.5).
The `rtr` object requires a boolean `enabled` and optionally a `commands` array drawn only from N3's fixed set; unknown keys and wider entries are `CONFIG_INVALID`.
`clientId` is required; profile names match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`.
Unknown keys or malformed documents produce `CONFIG_INVALID` without echoing their values.
The shipped package includes `falcon_axi/axi-credential.schema.json`, a schema of one profile with
`x-secret: true` on `clientSecret` for host injection.

POSIX reads reject non-regular files, symlinks, and a different owner before reading content.
Config files must not be group/world writable (`mode & 0o022 == 0`); SecretRef targets must have no
group/world permissions (`mode & 0o077 == 0`), so 0400 is accepted.
Windows reads ignore synthetic mode bits and reject all reparse points, including junctions.
`auth status` additionally verifies the protected DACL through one fixed, noninteractive PowerShell script,
requiring FullControl for only the current user, SYSTEM, and Administrators.
Ordinary commands do not launch that diagnostic process.
The platform and ACL verifier are injectable in the private-file module for offline Windows-branch tests.
Credential configuration remains read-only; the separate agent integration write surface is owned by §12.2.
Failures produce `CONFIG_INSECURE` with a path and platform-specific repair instructions.

`profile list` reports names without resolving secrets; `config path` reports config and journal paths.
`auth status` reports the selected profile, endpoint, and secret source before the existing bounded token
check result; no client ID, secret, token, or standalone CID is exposed.
`--config` and `--profile` are global flags and are replayed in follow-up commands with shell quoting.
The member CID may be stored in a user-owned profile because selecting a tenant requires its identifier.
Its standalone value is **never printed** unmasked, no v1 flag reveals it on its own, and it is never
committed to a repository.

The same tension applies to `--member-cid`, and the same resolution holds, with the exposure named rather than
softened.
The CID is deliberately accepted in `argv` because it is an identifier rather than a credential and because
per-invocation tenant selection is the only way to run one command against a child tenant without editing
configuration.
The cost is real and is the cost §5.3 names for every `argv` value: a CID passed as a flag is visible in process
listings, in shell history, and in agent transcripts, and unlike a bearer token it does not expire.
Two lower-exposure channels exist and should be preferred when that matters: a `memberCid` in a
user-owned profile, which is right when an operator works the same child tenant repeatedly, and
`FALCON_AXI_MEMBER_CID`, which is right when a shell session or an agent works one tenant for the session's
duration.
`--member-cid` is then reserved for a one-off invocation against a different tenant, and `--no-member-cid`
clears an inherited value without editing either channel.
Accepting the value as input says nothing about printing it back as a standalone member CID: §5.5 masks or
omits that value in output, and generated suggestions never echo it separately (§7.2).
Alerts v2 composite detection ids containing the selected child CID remain printed as-is and may be passed to
`detection show` (§5.5).

### 12.2 Session hook and skill

`falcon-axi setup` prints offline guidance and writes nothing.
`falcon-axi setup hooks` explicitly installs or repairs all three integrations, without authentication or network access.
Claude Code uses `~/.claude/settings.json` and Codex uses `~/.codex/hooks.json`, with `hooks.SessionStart` command entries, an empty matcher, and `timeout: 10`.
Codex additionally needs `[features] hooks = true` in `~/.codex/config.toml`.
OpenCode uses the managed `~/.config/opencode/plugins/axi-falcon-axi.js` plugin to inject local status into system context with a ten-second process timeout.
These four files are the complete write targets; setup installs no skill and accepts no `--app` flag.
`scripts/architecture_check.py` confines package file-mutation calls to `falcon_axi/setup.py`.
The `falcon-axi-session` marker identifies owned entries for idempotency and executable-path repair while preserving unrelated settings and hooks.
An unchanged installation makes no writes and prints only the TOON `hooks` object with `status`, `claude`, `codex`, and `opencode` results.
Malformed JSON or TOML and an unmanaged OpenCode plugin are refused before any file is written.
The command uses a PATH-verified `falcon-axi-hook` name only when an absolute PATH entry resolves to the installed sibling executable, otherwise an absolute path.
Both the installation path and resolved target must be durable: `/tmp`, linked git worktrees, `.treehouse`, `worktrees`, and `.no-mistakes` are refused.

The second console script, `falcon-axi-hook`, resolves credentials locally and prints one line containing version, profile resolution status, region when resolved, and one help command.
It never authenticates or runs the live home view, so session context costs zero network requests and requires no token cache.
On any error it prints one safe fallback line and exits 0, keeping session start usable without credentials or with invalid configuration.
The bare home view remains the live entry point for recent detections.

The installable skill is generated from the same content the home view prints, with live state stripped, and
the local required-check set runs its `--check` mode and fails verification when the committed skill files
drift, including missing or extra command references.
The skill's description states the read-only posture, so an agent loading it for a containment task learns
immediately that this is not the tool.

The generated `skills/falcon-axi/SKILL.md` ships independently of the `setup` command.
`uv run scripts/skill.py` generates the main guidance from shared home-view guidance, with no live state, and one `references/<command>.md` file per registered command.
The main file directs agents to `uvx falcon-axi --help` for the command list and to those references for individual command help, so adding a command does not rewrite a shared command index.
Its examples use `uvx falcon-axi` without requiring a global installation.
`uv run scripts/skill.py --check` fails on drift and runs in `scripts/verify.py`.
Operators install it with `npx skills add knowttl/falcon-axi --skill falcon-axi`; no agent configuration is written by ordinary CLI commands.
Only a bare home invocation may append that install hint, including when credentials are missing.
The host markers are `CLAUDECODE`, `CODEX_THREAD_ID` or `CODEX_SESSION_ID`, `PI_CODING_AGENT`, and `OPENCODE`, in that precedence order.
File-only checks suppress it when that host loads a `falcon-axi/SKILL.md` in its user or project roots, walking project ancestors through the repository root.
Claude uses `.claude/skills`, Codex `.agents/skills`, Pi its `.pi/agent/skills` user root and `.pi/skills` project root plus shared `.agents/skills`, and OpenCode its config `opencode/skills` user root and `.opencode/skills` project root plus Claude and shared roots.
The probe honors `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, and `XDG_CONFIG_HOME`, and Claude's main-checkout fallback for linked worktrees.
Custom roots in host settings and recursive skill layouts are outside this probe's scope.
Probe errors suppress the hint and never change the command result or exit code.

The `--all` rows describe the shipped walker; the README owns delivery status.
`N` counts query requests, including an empty terminal page when no total or terminal token established completion.
The table assumes each query page needs a hydrate request; an empty ID page needs none.
Per §7.1 and §7.2 a walk pages at `min(documented endpoint maximum, remaining row
budget, wall headroom)`, not at `--limit`.
For full pages starting at the beginning, with completion known from the final nonempty response,
`N` is `ceil(rows / 10000)` query pages for `detection`, `ceil(rows / 5000)` for `host`,
`ceil(rows / 100)` for `account`, and `ceil(rows / 5000)` for `vuln`, with `H` following the 1000-ID Alerts hydrate cap.
Here `rows` counts query rows (§7.2), including IDs lost before hydration.
`rows` is itself bounded by the governing wall where one applies, at 10000 for `detection` and 9999 for `host`,
so those two walks cannot exceed one and two query pages respectively no matter how large `--max-rows` is.
Neither accounts nor Spotlight has a v1 offset wall.

`detection list --all` and `host list --all` cost 3 requests,
and `vuln list --all` costs 2, the same as their single-page forms.
An `account list --all` walk returning 1000 accounts needs ten query/hydrate page pairs plus the token mint, or 21 requests.
A walk all the way to the §7.1 Alerts stop, `detection list --all --max-rows 25000`, costs 1 token + 1 query
page + 10 hydrate chunks and stops partial at 10000 rows, not the roughly 1000 requests a 20-row page size would
have cost.
`host list --all --max-rows 10000` costs 1 token + 2 query pages + 2 hydrates and ends at 9999 rows.

## 14. Offline fixtures and testing

### 14.1 The constraint, stated honestly

No live Falcon tenant or credential was available during this design task, and none is assumed to be
available during implementation.
Every test in the local required-check set therefore runs offline against fixtures.
This limitation belongs in the README, not buried here.

Section 15 owns the validation policy beyond the offline required checks.

### 14.2 The seam that makes it possible

There are exactly two implementations of the scoped-operation transport in §3.3: `HttpTransport`, which
prepares a permitted request and delegates network access only to `sendPermittedRequest`, and
`RecordedTransport`, which serves synthetic fixtures keyed on operation ID plus a hash of the request
arguments without any network access.
Both preserve the same sealed registered-operation and OAuth entry-point checks without adding a raw-URL
interface.

**The substitution is compile-time and test-only.**
Section 3.3's sealed module exports only `request` and `requestOAuthToken` and exposes no injection point, and
that is deliberate: a runtime-selectable transport, and especially one keyed on an environment variable, would
be a seam around the very registry checks §3.3 presents as unbypassable.
So `RecordedTransport` is never selected at runtime.
Offline tests build against it by module resolution at build and test time, the shipped binary contains only
`HttpTransport`, and no flag, environment variable, config key, or exported setter can reach the recorded
implementation in a released build.
Because the entry-point checks live in the sealed module rather than in either implementation, substituting one
for the other cannot drop a check.

Domain modules are pure functions from arguments to request descriptors, and from responses to TOON.
So every command is testable end to end with no network and no mocking framework, which is `awx-axi`'s
`RecordedTransport` pattern and `azure-axi`'s transport-seam rule arriving at the same shape.

### 14.3 Layout

```
test/
  fixtures/
    alerts/          GetQueriesAlertsV2, PostEntitiesAlertsV2
    hosts/           QueryDevicesByFilter, PostDeviceDetailsV2, QueryDeviceLoginHistoryV2
    discover/        query_accounts, get_accounts
    spotlight/       combinedQueryVulnerabilities
    oauth2/          token success, 401, 403-with-member-cid
    errors/          400 FQL, 403 scope, 429 with and without X-RateLimit-RetryAfter, 500, 503
  offline/           one file per core seam and per domain
  support/           fixtures.ts, toon.ts, run.ts
```

Each fixture file carries a provenance header with the operation ID, the official schema or operation
reference URL, the referenced schema version or retrieval date, and `provenance: synthetic`.
There is no capture date or captured/hand-authored distinction because no fixture is derived from a tenant.

### 14.4 Wholly synthetic fixtures

Every fixture is wholly synthetic and authored from the documented response schemas cited in §18.
No live Falcon response, scrubbed live response, transformed telemetry, tenant identifier, or customer datum
is committed in any form.
The same bar covers people: do not commit a real name, login, email, home path, employer name, hostname,
address, credential, or private workflow path, in docs, commits, or pull-request text.
Clean those out before they reach the repository, and use synthetic fixtures and neutral wording instead.
There is no recorder mode, capture-to-fixture path, or denylist-based claim that a response is safe after
selected fields are removed.
A denylist cannot prove that a newly introduced telemetry field contains no customer data.

This accepts the self-confirmation risk explicitly.
`azure-axi`'s recorded lesson is that a hand-authored fixture proves only that the code agrees with its author,
so offline fixtures prove deterministic behavior but not upstream fidelity.
Section 15 owns the validation policy and its limits; offline fixtures alone cannot establish upstream fidelity.

Two offline tests enforce repository hygiene: one asserts that every fixture has the complete synthetic schema
provenance header, and one asserts that no fixture matches credential, token, CID, or realistic tenant-data
patterns.

### 14.5 The tests that carry the design

The highest-value offline tests are the ones covering behavior a naive client gets quietly wrong:

- **Registry integrity** (§3.3): exactly the operations in §2.1; every one `effect: "read"` except
  the two in `SEARCH_LIFECYCLE_IDS`, the one in `GRAPHQL_QUERY_IDS`, N3's four execution ids, and N4's two `MALQUERY_SEARCH_IDS`; every one with complete evidence and a
  doc scope matching its tier; runtime
  registry validation rejects unknown IDs or descriptor mismatches before network access; and attempted
  mutation of each frozen descriptor, `scopes` array, `evidence` object, and the outer record leaves every
  canonical value unchanged.
  This is the mechanical form of Invariant R and it fails local verification, not a review.
- **The second enforcement tier is closed** (§3.3 property 2, §4.3): sealing a `search-lifecycle` descriptor
  whose id is not in `SEARCH_LIFECYCLE_IDS`, or whose scope tuple is anything but `["NGSIEM:write"]`, fails
  at registry construction; and a `read` descriptor carrying any `:write` scope fails too, so the write scope
  cannot be smuggled in under either tier.
- **The third enforcement tier is closed, and GraphQL has one way in** (§3.3 properties 2 and 8, §4.4): sealing a
  `graphql-query` descriptor whose id is not in `GRAPHQL_QUERY_IDS`, whose scope tuple is anything but
  `["Identity Protection GraphQL:write"]`, or whose verb is not POST fails at registry construction, and
  neither exception's id can claim the other's effect; every registered document parses with `graphql-core` as
  exactly one `query` whose root fields satisfy §3.3 property 8's allowlist, and declares exactly the variables it
  uses; the runtime seal refuses a document that is a mutation, has a second operation, a fragment, a string,
  a comment, or a write scope; the transport refuses a body, an unregistered document name, or an undeclared
  variable for the GraphQL operation, and refuses a document for any other operation; a hostile value is
  carried in `variables` and never appears in the query text; and the network sink refuses any GraphQL body
  that is not a registered document even with a valid permit.
- **Path variables cannot retarget a route** (§3.3 property 7): a `--repository` containing `/`, `\`, or `%`,
  or equal to `.` or `..`, is refused with `VALIDATION_ERROR` before any request; a prepared variable set
  that does not match the route's declared set fails `READ_ONLY_VIOLATION`; and the offline transport runs
  the same check, so the test seam cannot be more permissive than the sealed one.
- **NG-SIEM search lifecycle**: cover §4.3's creation, optional bounded polling, recovery, cancellation, and query-error contracts, with rendering as specified in §10.2.
- **N4 search boundary** (§4.6): synthetic CLI tests prove fuzzy metadata, exact request creation and status reads, result caps, READ_ONLY precedence, and licensed/permission-denied guidance.
  Registry tests reject widened ids, scope tuples, methods, paths and relabelled effects; sink tests reject unchecked bodies and query parameters even with valid permits.
  Search POST replay tests verify a single send on retryable errors, and the excluded MalQuery ids stay absent.
- **N3 before delivery** (§4.5): exercise the real CLI and sealed transport with synthetic responses for passive history reads, disabled opt-in, narrowed lists, exact host/command confirmation, READ_ONLY precedence, command-injection refusal, sink body checks, journal failure, and the one-host lifecycle.
  Assert bounded acquisition and unconditional deletion on success, execution failure, polling failure, timeout, cap exhaustion, and interrupt, including explicit failed/unknown cleanup outcomes and ambiguous-send replay refusal.
  No source-string test substitutes for these behavioral checks; `tests/offline/test_rtr_execute.py` covers the internal core and shipped CLI, including real SIGINT/SIGTERM delivery against fake responses.
  The shipped history slice is covered by `tests/offline/test_rtr_history.py`.
- **Directory and GraphQL timeline reads never treat a GraphQL failure as an empty result** (§4.4): each GraphQL identity command
  sends one registered document with its filters as variables; `--type` selects a document rather than building
  one; a cursor is bound to its filters and a timeline cursor continues the window it started; an entity id that
  is not a GUID is refused before any request; a 403 names `Identity Protection GraphQL:write` and the
  document's read scope with the reason the scope is labelled write; a 400 is `UPSTREAM_ERROR` and never FQL
  advice; and an `errors` list on HTTP 200, with or without partial `data`, is `UPSTREAM_ERROR`.
- **Network architecture boundary** (§3.3): an independent source/import scan allows network imports only in
  `falcon_axi/transport/harness.py`, allows those bindings to be referenced only by its `send_permitted_request`
  function, and rejects them everywhere else, including every other function in that file and the sealed
  transport module; only `APIHarnessV2` may be imported from `falconpy`; process and shell execution are
  rejected outside the explicitly reviewed allowlist, whose entries are the fixed
  `private_file.py` PowerShell DACL diagnostic and the sink's fixed Python request worker with a remaining-budget timeout, and the check rejects other shells,
  network-capable executables, dynamic executable selection, and any `subprocess` call site not on that
  allowlist; the sink rejects a prepared request without a valid module-local permit before network access.
- **Hydrate chunking**: 2500 alert IDs produce three hydrate requests of at most 1000 each, and the assembled
  order matches the query-step order.
- **Pagination across two models**: an offset walk that reports the server's `total`, a token walk that carries
  `after` opaquely, a Hosts request that preflights the confirmed `limit + offset` rule, and an Alerts offset
  walk that stops at v1's explicitly defensive 10,000-result boundary.
- **Walk page size and wall headroom**: an `--all` walk requests each page at `min(documented endpoint maximum,
  remaining row budget, wall headroom)` regardless of `--limit`, and chunks the Alerts hydrate step at 1000 IDs;
  a `detection list --all` to the default 1000-row cap issues one query page and one hydrate request, not fifty
  page pairs; `host list --all --max-rows 10000` requests its second page at limit 4999 and ends at 9999 rows
  rather than surrendering at 5000; and a non-walking call still returns exactly `--limit` rows.
- **Explicit partial results**: whenever an `--all` walk stops early, exit 0 output contains `partial: true`, a
  `stop_reason` of `max_rows` or `pagination_limit`, and a help line matching that stop, and the count uses the
  server total when available; a cap that does not truncate emits no partial marker.
- **Cursor emission tracks reachability, not `stop_reason`** (§7.2): a `max_rows` stop below the governing wall
  carries a `continuation_cursor` that resumes through §7.2's cursor contract; a `pagination_limit` stop carries
  none; and the boundary case pins the rule, `host list --all --max-rows 9999` spending its budget precisely at
  the cited `limit + offset` ceiling emits `stop_reason: max_rows` with **no** cursor and a help line stating
  both that the budget was spent and that the remaining rows are unreachable.
  The governing wall is named per endpoint, since the Hosts ceiling is cited to a captured 400 body while the
  Alerts one is defensively enforced and unverified (§7.1, §17).
- **A wall retains rows**: a Hosts or Alerts walk that reaches a §7.1 wall after fetching rows returns those
  rows at exit 0 with `stop_reason: pagination_limit` and no cursor, never an error envelope, while the same
  wall reached with no rows retained returns `PAGINATION_LIMIT` at exit 1.
- **Home-view truncation disclosure**: a query total greater than the five rendered rows produces the free
  `count: N of M total` line and continuation help; a full five-row page without a total produces `more: true`
  and the same help; neither path makes an additional request.
- **Cursor context binding**: changing the effective query, sort, region, member-CID, client ID, client secret,
  operation, model, or position causes the shared decoder to reject the cursor with `VALIDATION_ERROR` before
  any request; the token contains no credential or CID value; generated next-page suggestions replay every
  non-sensitive required context flag including an explicitly supplied `--allow-unknown-origin`; and a
  member-CID continuation refers to the prior tenant selection without printing its value.
- **Missing total**: a response with no `meta.pagination.total` renders `of unknown total`, never a fabricated
  count.
- **Rate limiting**: a 429 with a future `X-RateLimit-RetryAfter` waits and retries; one with a past or
  malformed value falls back to backoff; a 503 with the header present ignores it.
- **Error translation**: synthetic schema-valid bodies for 400 FQL, 403 scope, and 500, asserting the
  translated output and specifically that no raw Falcon body, status number, or endpoint path appears on
  stdout.
- **TOON conformance**: every stdout fixture parses in TOON v4.1 strict mode; colon-bearing tabular cells stay
  quoted; help elements retain their declared count and escaping; and truncation metadata remains a valid
  scalar rather than an over-indented child of a primitive.
- **Redaction**: a response and a debug log containing every key in §5.5, asserting none reaches either stream.
- **The secret-name flag guard** (§5.3): the guard rejects `client-secret` and other secret-shaped names.
- **Atomic environment credentials**: either environment variable without its pair yields
  `CONFIG_INVALID`, names the missing half, and never falls back to a file profile.
- **Credentials and config file provenance** (§5.2, §12.1): unsafe files yield `CONFIG_INSECURE` before content
  is read; config files prohibit group/world writes, while SecretRef targets prohibit all group/world bits.
  Offline tests exercise Windows synthetic modes, reparse-point refusals, and diagnostic ACL verification
  through fakes; no real Windows DACL run is claimed.
- **Trusted origin**: HTTP, userinfo, explicit non-default ports, non-root paths, query or fragment URLs,
  redirects, and non-allowlisted hosts are rejected before token minting; the error reports only the violated
  component and allowlist and never the URL or component value, including when an arbitrary query value equals
  a secret; `--allow-unknown-origin` admits an HTTPS unknown host only for that invocation and has no
  environment or profile equivalent.
- **Region autodiscovery**: a token response whose `X-Cs-Region` differs re-targets exactly once, including a
  308 with an empty body; `Location` is never read; an unknown region yields `REGION_MISMATCH`, preserves the
  observed region text, fabricates no short name, and points to the verified-full-URL plus
  `--allow-unknown-origin` remedy; a missing region header or a second redirect is `ORIGIN_NOT_ALLOWED`.

## 15. Safe live-test boundaries

This section is a hard rule of the test design, not a recommendation.

### 15.1 What may ever run against a real tenant

Decision, 2026-10-18: no owner live run is required and no `tests/live/` suite will be built.
Validation uses offline synthetic fixtures and source parity with CrowdStrike's falcon-mcp, with falconpy and official API references where falcon-mcp has no corresponding tool (§17).
This closes the delivery questions without claiming tenant validation.
The following boundaries remain requirements for any separately authorized future live validation, not a description of an existing suite.
Only the operations in §2.1 could be exercised, through the sealed transport.

**Any future live validation may never issue a mutating operation outside N1, N3, and N4, or GraphQL text outside N2's registered documents.**
N3 and N4 grant no live-test authorization in this amendment.
MalQuery search is verified exclusively with synthetic offline responses; no licensed tenant or live search is required or authorized.
Any separately authorized N4 validation must retain its exact/fuzzy-only pattern and result bounds, and must never hunt or download malware.
Passive history reads must remain passive; a separately authorized RTR execution must use the opted-in profile, exact host/command confirmation, fixed allowlist, bounded output, durable redacted journal, and unconditional deletion in §4.5.
The closed operation tiers, scope restrictions, and registered GraphQL document boundary are owned by §3.3.
Property 9 owns N3's additional transport enforcement; §19 records its implementation slices.
Any future live harness must add a second assertion: it interposes at
the private network sink, rejects any request without the transport's module-local permit, records every
scoped operation ID and every GraphQL document name issued during the run, and fails if the operation set is
not a subset of §2.1 or a document name is not in the document registry.
A live run that starts an NG-SIEM search through any command in §4.3 must also stop the job it started in the same test, so the suite
leaves no running job behind.
An RTR execution validation must delete its session in the same invocation even on failure, timeout, or interrupt, and assert cleanup completion rather than accept a lingering session as a pass.
Its sink recorder must additionally verify the N3 command and host/session authorization; a missing or unknown cleanup result makes validation incomplete or failed, never successful.
The registry check, source-level network boundary, and sink recorder are separate controls, so one forgotten
call site does not silently bypass all three.

### 15.2 Credentials for live tests

Any separately authorized live validation would require an API client provisioned per §5.7: read scopes, plus `NGSIEM:write` only if the
run is to exercise a command requiring that scope under §4.3, and `Identity Protection GraphQL:write`
only if the run is to exercise the fixed GraphQL identity queries.
For separately authorized N3 validation, add `Real time response:read` only for its six named RTR operations and `Real time response audit:read` only for the audit read.
For execution validation, the profile opt-in and READ_ONLY precedence still apply; API grants do not bypass those guards.
For separately authorized N4 validation only, `MalQuery:write` permits its two search ids and `MalQuery:read` permits status; licensing availability is unverified.
Provisioning would be the operator's guarantee to make: falcon-axi cannot verify it (§8.2).

The credential is sourced from the environment or a §5.2 SecretRef and is never written anywhere,
never printed, never included in a fixture, never in a log, and never in a failure message.
Any future live harness must retain responses only in memory for shape validation and have no persistence interface.

### 15.3 Requirements for any future live validation

**Shape, not content.**
Each operation that the tenant can exercise must return a successful response with the expected documented
envelope and schema.
A 4xx, 5xx, translated error code, wrong path, or malformed envelope fails that operation's smoke check rather
than counting as an acceptable documented outcome.
The harness asserts only schema and envelope shape in memory, never a specific detection ID, hostname, CID, or
vulnerability, so it stays valid as the tenant changes and no tenant detail is baked into the repository.

The complete live check has concrete data preconditions: at least one alert ID to exercise
`PostEntitiesAlertsV2`, at least one host ID to exercise `PostDeviceDetailsV2`, a schema-valid Spotlight filter,
at least one observed account ID to exercise `get_accounts`, a host ID for login history,
and enough results in at least one list domain to produce a continuation.
A successful empty query response still validates that query operation, but it cannot validate its hydrate
operation or pagination.
When a precondition is absent, the affected operation or pagination assertion is reported as `SKIPPED` and the
suite result is explicitly **validation incomplete**, never a pass.
A complete smoke pass therefore means all operations in §2.1, all registered GraphQL documents, and one
paginated continuation succeeded, with the
NG-SIEM job the pass starts also stopped by the same pass, and any N3 session it opens deleted by the same invocation (§15.1); a changing or sparse tenant, or a
credential without `NGSIEM:write` or without the Identity Protection scopes, may instead produce an honest
incomplete result.

Such validation must not provoke 4xx or 5xx responses.
Section 9.4's synthetic error translations remain provisional until a real error body is safely observed.

### 15.4 Local required checks and the automated boundary

The captain authorized the offline gate in `.github/workflows/ci.yml` and PyPI release automation in `.github/workflows/release-please.yml`.
The Python amendment's §8 owns release-please and Trusted Publishing behavior.
See [Contributing guide](../../CONTRIBUTING.md) for its invocation and triggers.
Any other automation, and any workflow that needs a Falcon credential, remains a captain decision.
The single local verification entry point is `uv run scripts/verify.py`; it runs the entire
offline required-check set described in §14.5, including lint, offline tests, registry integrity, the exact-sink
network boundary, fixture hygiene, skill drift `--check`, and the repository scan described below.
[`scripts/verify.py`](../../scripts/verify.py) defines the check sequence, with the offline pytest suite under a socket guard.

- **There is no live suite or live opt-in to run.**
  `uv run scripts/verify.py` remains entirely offline; no branch, `main`, schedule, or repository event runs Falcon calls.
- **No Falcon credential is stored in an automated service**, so there is nothing for automation configuration
  or a compromised dependency to reach.
- **No fixture recorder exists**, so neither a required check nor a live invocation can persist responses.
- `scripts/architecture_check.py` rejects every entry under `.github/workflows/` except the files `ci.yml` and `release-please.yml`,
  and rejects `.gitlab-ci.yml`, `.circleci/`, `azure-pipelines.yml`, and `Jenkinsfile`.
  It rejects any reference to `FALCON_AXI_LIVE`, `FALCON_AXI_CLIENT_ID`, `FALCON_AXI_CLIENT_SECRET`,
  `FALCON_CLIENT_ID`, or `FALCON_CLIENT_SECRET` in either authorized workflow.
  These names remain legitimate outside automation configuration, including in the credential resolver and this design.
  Other automation, including `*.service` and `*.timer` units and crontab-shaped files, remains unauthorized,
  but is not covered by the current repository scan.
  Inert repository metadata such as `CODEOWNERS` or an issue or pull-request template is neither automation that
  can reach a credential nor forbidden, and it must not fail local verification; the same goes for a
  `.pre-commit-config.yaml` used purely for local formatting.
  The workflow scan is the one place the env-var clause bites on today's tree: neither workflow may name them.

`awx-axi` reached the stronger conclusion that a gated write suite should be deleted rather than gated, because
"a gate that exists can be opened by a future contributor who has not read the captain's order".
falcon-axi inherits that reasoning and does not need a general tenant-write gate: only the closed captain exceptions are admitted (§0).
Local integration writes (§12.2) are covered offline by `tests/offline/test_setup.py`.

### 15.5 The coverage cost, stated plainly

The live suite is absent by owner decision, rather than outstanding delivery work.
Historical manual observations in §18 retain their original limited scope.
The parity closures in §17 are source checks, not a smoke pass: scopes, licensing, audit visibility, successful Discover account responses, and the tenant's GraphQL schema have not been validated by this decision.
No tenant credential or captured response is needed for the required checks.

## 16. API client evaluation

### 16.1 What CrowdStrike actually publishes for TypeScript

**Package**: `crowdstrike-falcon` on npm.
**Source**: `github.com/CrowdStrike/falconjs`, MIT.
**Latest release**: v0.7.0, published 2026-07-23; the repository HEAD read for this evaluation is `4e4f210`,

**Coverage**: 144 API classes under `src/apis/` and 2,936 model files under `src/models/`, generated from
CrowdStrike's swagger (recent release commits are "Regenerate the codebase using swagger 2026-05-07" and
"2026-07-13").
The Developer Center lists TypeScript alongside Python, Go, Rust, Ruby, and PowerShell as a supported SDK, and
every operation page carries a TypeScript tab.

**Dependency weight**: zero runtime dependencies, which is genuinely good.
But the npm registry reports the published package at **19.9 MB unpacked across 5,565 files**, and the
checked-out `src/` measures 20 MB.
falcon-axi v1 calls only the operations in §2.1.

**Maintenance state, stated from the repository rather than from reputation**:

- The README says, verbatim: "falconjs is an open source project, not a CrowdStrike product.
  It carries no formal support, expressed or implied", under a heading reading **Experimental**.
- `package.json` declares `"test": "echo \"Error: no test specified\" && exit 1"`.
  There is no test suite.
- The version is 0.7.0.
  Releases are frequent and recent, so it is maintained; it is not stable-versioned or formally supported.

**What it actually does for us:**

| Need | falconjs |
| --- | --- |
| OAuth2 client-credentials flow | Yes; `src/middleware/oauth2.ts` mints, caches in memory, and collapses concurrent refreshes |
| Flight Control member CID | Yes; `memberCid` is passed to `oauth2AccessToken` |
| Region base URLs | Yes, the same four as §6.1, in `src/FalconCloud.ts` |

including every mutation surface** inside falcon-axi's dependency tree.
That does not by itself violate the invariant, since §3.3's registry is what decides what is issued, but it
does mean the code that could contain a host is present and one import away, rather than absent.
A five-operation hand-written client makes the invariant visible in the file listing.
This is a supporting argument, not the deciding one.

### 16.2 The alternative: a thin client over `fetch`

Node's native `fetch`, the closed registered-operation request and sealed OAuth path in §3.3, and five
operation descriptors.
The pieces falcon-axi would own:

1. `POST /oauth2/token` with `client_id`, `client_secret`, and optionally `member_cid`, form-encoded, reading
   `access_token` and `expires_in`.
   Roughly 30 lines, verifiable against falconjs's `oauth2.ts` and falconpy.
2. Reading `X-Cs-Region` and re-targeting (§6.4).
   The SDK does not provide this, so it is owned either way.
3. Pagination normalisation across the models in §7.1.
   The SDK does not provide this either.
4. Retry and backoff (§7.4).
   Same.
5. Error mapping (§9.4).
   Same.

### 16.3 Recommendation

**Adopt the thin `fetch` client for v1.
Use falconjs as a reference, not as a dependency.**

The deciding tradeoff, in one line: **the SDK covers only the one part falcon-axi could write in thirty lines,
and covers none of the four parts that are actually hard.**

Supporting reasons, in order:

- Pagination, rate limiting, region autodiscovery, and error translation are the entire substance of §7, §9,
  and §6.4, and falconjs supplies none of them.
  Adopting it would not reduce the code falcon-axi must write; it would only move where the token request
  lives.
- 19.9 MB and 5,565 files to reach a handful of operations is a poor exchange, particularly for a CLI an agent may run
  through `npx`.
- The upstream's own words are "Experimental" and "not a CrowdStrike product... no formal support", with no
  test suite.
  That is not a reason to avoid reading it, but it is a reason not to put it on a security tool's critical path
  when it buys so little.
- The commission's constraint, "do not reimplement OAuth2 token handling or pagination blindly", is honored by
  *consuming Falcon's own mechanisms* rather than inventing parallel ones: falcon-axi mints tokens at Falcon's
  documented endpoint, follows Falcon's own `after` tokens and `meta.pagination` counts, and obeys Falcon's own
  `X-Cs-Region` and `X-RateLimit-RetryAfter` headers.
  It invents no token format, no cursor scheme beyond an opaque wrapper over Falcon's own position values, and
  no rate model.

**The revisit trigger, written now so it is not a matter of taste later**: if falcon-axi's registered operation
count passes roughly 30, or if falconjs ships a stable 1.0 with a test suite and formal support, re-run this
evaluation.
Hand-writing thirty typed operation descriptors is fine; hand-writing a hundred is not.

**Recorded honestly**: adopting falconjs would give a typed model for every response field, which the thin
client does not.
falcon-axi's answer is that it prints 4-field TOON rows from a small hand-written response type per operation,
so full response typing is worth less here than it would be in an application.

### Where the siblings' assumptions do not transfer to Falcon

Called out explicitly, because copying any of these would produce a wrong design.

1. **Ambient credentials.**
   `azure-axi` owns no credentials at all: it relies on `DefaultAzureCredential` and whatever `az login` left
   behind.
   Falcon has no ambient credential, no local login state, and no first-party CLI, so falcon-axi must own the
   OAuth2 client-credentials flow itself (§5, §16).
2. **Read-only enforced by HTTP verb.**
   `awx-axi` can guarantee no writes by declaring no `DELETE`/`PUT`/`PATCH` route and having exactly one
   mutating method on its transport.
   Falcon reads are routinely POSTs (`PostDeviceDetailsV2`, `PostEntitiesAlertsV2`, `getChildrenV2`), so the
   verb carries no safety information and the boundary must be a closed operation registry (§3.3).
   `azure-axi` hit a narrow version of this ("an ARM route that is a POST is still a read"); in Falcon it is
   the norm, not an exception.
3. **A scope string implies safety.**
   Neither sibling has this trap.
   In Falcon, `Real time response:read` covers session creation and command execution on a live endpoint
   (§4.1), so scope names cannot serve as a read/write test and §2.2 needs a second citation.
4. **One base URL from configuration.**
   `awx-axi` reads a single `CONTROLLER_HOST`.
   Falcon has at least four regional base URLs plus a documented autodiscovery mechanism via `X-Cs-Region`
   (§6.1, §6.4).
5. **A hierarchical scope selector.**
   `azure-axi`'s `--scope` walks a subscription and management-group hierarchy, per request.
   Falcon's tenancy is a flat parent-child CID relationship bound **at token mint**, so tenant selection is per
   invocation and cross-tenant queries are impossible in one call (§6.5).
6. **One uniform pagination envelope.**
   `awx-axi` follows a single `{count, next, previous, results}` shape and a server-provided `next` URL.
   Falcon has three pagination models, no `next` URL, a cursor that appears in different places by endpoint
   family, a confirmed Hosts `limit + offset` rule, and a defensively enforced but unverified Alerts stop
   (§7.1).
7. **One row limit per resource.**
   Neither sibling has a query cap and a hydrate cap that differ.
   Falcon queries 10,000 alert IDs and hydrates 1,000 at a time (§2.3), so the client must chunk.
8. **Long-lived tokens.**
   AWX personal access tokens are effectively unbounded, so `awx-axi` stores one and never refreshes.
   Falcon tokens last 30 minutes, which is what makes "no token cache" a reasonable v1 position (§5.4).
9. **Rate limiting is not modelled.**
   Neither sibling designs for throttling as a first-class failure.
   Falcon publishes rate-limit headers on every response and a retry-after header on 429, and a security API
   under an agent's `--all` walk will hit it (§7.4).
10. **The filter language.**
    KQL (`azure-axi`) and Django-style lookups (`awx-axi`) are both guessable from general knowledge.
    FQL is not: `+` for AND and `,` for OR is the opposite of most conventions, which is why §11.3 makes it a
    discovery problem rather than a documentation problem.
11. **Fixture sensitivity.**
    `awx-axi` redacts SCM credentials from captured logs, but Falcon responses are security telemetry about
    real machines and a denylist cannot prove a response safe.
    Section 14.4 therefore permits only wholly synthetic fixtures and commits no captured or scrubbed live
    response.

## 19. N3 implementation slices

Land these in order, preserving the public delivery status until each slice is actually implemented.

1. **R1: history reads.**
   Implemented as `rtr session list`, `rtr session show <id> [--full]`, and `rtr audit list`.
   Lists accept `--filter`, `--limit` (default 20, session ceiling 5000, audit ceiling 1000), and opaque `--cursor`.
   Session queries retain upstream totals and order across POST hydration in batches of 100 ids.
   Audit reads combined records without hydration or command-info expansion.
   Both default to `id`, `hostname`, `user_id`, and `created_at`; session detail returns redacted metadata with bounded text previews.
   Missing totals stay unknown; empty pages terminate continuation, and cursors bind operation, filter, origin, tenant, and credential.
   READ_ONLY permits these passive reads without execution opt-in or confirmation.
   Missing scopes name the appropriate RTR or audit read permission and explain subscription-dependent availability.
   Exact id/method/route/scope admission tuples seal both RTR collections; every other RTR operation remains refused.
   Synthetic fixtures, recorded invocations, and offline transport refusal tests provide source-parity evidence only, with no live call.
   Only `RTR_ListAllSessions`, `RTR_ListSessions`, and `RTRAuditSessions` are added as ordinary reads with §4.5's two citations, exact route exceptions, bounded pagination, synthetic fixtures, and scope/discovery updates.
   No session creation or execution ships in R1.
2. **R2: execute core, implemented without a user-facing command.**
   Add the strict profile opt-in and subset-only command restriction, command grammar, exact authorization model, fourth transport tier, READ_ONLY precedence, replay policy, durable redacted journal, and the narrowly revised local-write architecture boundary.
   Fix finite execution/cleanup budgets and output byte/chunk caps, and resolve ambiguous-init ownership and recovery without widening the operation allowlist.
   Verify refusal paths and cleanup behavior offline before exposing execution.
3. **R3: `rtr run`, implemented.**
   Exposes the local preview and exact `--execute --confirm` contract, composes init -> execute -> bounded poll -> ALWAYS delete, and verifies the offline lifecycle and interrupt cases in §14.5.
   Generated help, scope matrix, skill, operator guidance, and request-cost documentation include the shipped surface.
   Golden command references deliberately add `rtr run` to help, unknown-command discovery, and scopes; top-level help now names N3's guarded execution rather than implying no session execution exists.
4. **Release.**
   Release falcon-axi with R1-R3 verified offline; no live call is a release prerequisite or implicitly authorized.
5. **artium-axi write-switch exposure, separate PR.**
   Only after that release, expose the capability through artium-axi's write switch in a separate artium-axi PR, retaining falcon-axi's profile opt-in, exact confirmation, and READ_ONLY override.
