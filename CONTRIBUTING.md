# Contributing

Use Node 22.18.0 or newer with the pnpm release pinned by `packageManager` in `package.json`, provided through Corepack.
Then run the complete local verification gate:

```sh
corepack pnpm install --frozen-lockfile --ignore-scripts --config.confirm-modules-purge=false
corepack pnpm run verify
```

To run it the way the validation pipeline does, with an empty throwaway home directory and no `FALCON_AXI_*` variables, prefix each command with `node scripts/isolated-home.mjs`.

The gate runs TypeScript compilation, formatting, architecture and generated drift checks, package installation checks, the cumulative native suite, and golden/safety provenance reconciliation.
GitHub CI installs the locked dependencies and runs the same offline verification on pull requests and pushes to `main`.
Both jobs in the release workflow are disabled during cutover; the first npm publication is manual from merged `main`.
See the [build and offline verification instructions](docs/design/v1-typescript.md#build-and-offline-verification) for runtime and Linux test prerequisites.

## Tests and fixtures

Response fixtures are wholly synthetic and carry provenance headers.
Installed-artifact tests use loopback-only namespaces or inherited kernel socket denial, so their synthetic delivery cannot contact Falcon.
Never commit credentials, tenant identifiers, captured responses, or personal data.
The released package contains no recorded transport or test-origin selector.

Run a focused slice with `corepack pnpm run check:slice --slice S13 --paths native --offline`, or execute the relevant compiled Node test using the same isolation setup as the slice runner.
The Python sources in `tests/offline/`, `tests/packaged/`, and `tests/support/` are frozen comparison provenance, not an executable suite for the current implementation.
Their selected source hashes remain checked by the TypeScript safety ledger; no Python runtime is needed to read them.
The recorded-invocation gate in `tests/golden/` preserves the output contract described in [the Python design](docs/design/v1-python.md#5-behavior-that-must-not-change-during-the-port).
Do not regenerate expected output to make a failure disappear.
Intentional behavior changes need a design explanation and a comment in the affected scenario.
Offline fixtures prove deterministic behavior; they do not establish tenant validation.

<!-- BEGIN canonical test-quality rules -->
**Test quality.** Write and review every test against these rules.
Tests are never required first; a change is verified end to end against the behaviour the user expects.

1. Trust upstream invariants: do not test states that types, schemas or database constraints already rule out.
   Test invalid input only at the boundary that validates it.
2. Assert outcomes from an agreed source (spec, domain rule, ground-truth fixture), never values copied from what the code returns today.
3. Mock only true external boundaries, with schema-valid or recorded payloads.
   Never mock in-process code.
   Delete tests that only check how a mock was set up or called, unless that call is the requirement.
4. Test through the public interface: no private helpers, internal state or internal call counts.
5. Every assertion must be able to fail when the behaviour breaks: no existence-, type- or constant-only assertions.

Exempt: validation-boundary tests, contract tests against an agreed schema or recording, and regression tests that cite the bug they reproduce.
<!-- END canonical test-quality rules -->

## Generated documentation

Regenerate the skill, its per-command references, and the invocation catalog from TypeScript metadata and templates:

```sh
corepack pnpm run generate
corepack pnpm run verify
```

`src/metadata.ts` owns command declarations; the README summarizes command groups.
`docs/commands.md` retains the generated Python-origin reference whose command surface is preserved by the migration parity gate.
Edit the metadata and templates rather than generated skill content or the invocation catalog.
The retained command reference is checked for parity, not regenerated by this command.
Every advertised command must exist in the TypeScript registry and its generated references.

## Architecture and review

Read the [design index](docs/design/README.md) before changing command behavior or implementation structure.
Preserve the [read-only boundary](docs/read-only.md), closed operation registry, and single network sink.
Each new endpoint needs the documented scope and first-party corroborating evidence in its registry entry.
Use conventional commit titles and keep pull requests focused on a reviewable behavior change.
Do not hand-edit the generated changelog.

## Releases

The release-please configuration uses the distinct `npm-v` tag namespace.
The `.github/workflows/release-please.yml` workflow publishes to npm through trusted publishing when a release is created.
Prereleases (`1.0.0-rc.N`) publish under `next` and never become `latest`.
Release-please updates `package.json`, the lockfile root version, `src/version.ts`, and the manifest together, so do not edit them by hand for a release.
Python artifacts remain installable, and a final notice-only PyPI release is separately gated on confirmation of the first npm publication.
Keep release mechanics in the workflow and package metadata; install examples should not pin release versions.
